# 設計判断の前の業界調査は四方向を一次資料で揃え、否定側も同じ重さで集める

Status: accepted — 2026-09-22 ユーザー指摘「調査のずさんさ」を恒久ルールに

## Problem

設計判断を、ベンダー一社の資料、自分の既存コードのコメント、一件の逸話、部下の要約だけで下していた。「根拠のない意見は意味がない」。

## Decision

調査は次の四方向を揃えてから判断に使う。

1. ベンダーの公式文書と出荷物(何を出し、何に使えと言い、何を注意しているか)
2. 著名な実践者本人の文章(どう運用し、何を言っているか。試して戻った記録を含む)
3. 測定された証拠(論文、ベンチマーク、issue の数字。研究タスクとコーディングを区別する)
4. 公開リポジトリの実態(採用数、鮮度、保守状態、事故の報告)

主張ごとに URL を付け、要所は原文を引用し、要約経由の引用と推測にはその印を付ける。否定側(廃止、保守モード、コスト事故)を肯定側と同じ手間で集め、issue は否定に偏り宣伝は肯定に偏ることを明記する。部下に出させた成果物は本文を全部読む。自分のコード、過去の設計書、置き換え対象の既存実装を根拠にしない。出すときは見出しを主張にし、結論・根拠・分かっていないこと・問いの順で、一つの grill に一つの問い。

## Alternatives considered

- **一次資料一社で足りるとする**: Anthropic の資料だけで workflow を語り、後の四方向調査で結論が覆った(多エージェントはコーディングで単体より悪い)。却下。
- **逸話一件で決める**: marmelab の整形フックの記録一件で Stop 案に傾いたが、公開リポジトリの主流は編集ごとの整形と Stop の関門の併用だった。却下。
- **要約だけ読む**: 要約は肯定側に寄り、否定の数字が落ちる。却下。

## Consequences

- 調査に時間がかかる(今日は一領域あたり部下 2〜4 本、各 15〜20 分)。その分、判断の手戻りが減る。
- この手順は `agents/research.md` のサブエージェント定義として五ハーネスから同じ形で呼べるようにする(未実装)。
