# Is spec-driven development (SDD) for coding agents good practice, or a fad? (2026)

Question this record answers: should the owner keep the `sdd` skill (spec/plan/tasks documents authored up front, then implemented against) as the default heavy path, or is "grilling" (interrogate the design in chat until it holds, then write a short decision record) the better default, with SDD reserved for something narrower?

Date: 2026-09-22. Method: four-lens survey per `domains/dev/llm/harness/agents/research.md`, executed via four parallel subagents (one per lens), each using direct `WebFetch`/`curl`/`gh` calls — WebSearch was not used (per instruction, treated as unreliable this session). Every claim below is attributed to a lens-agent and carries the URL that agent fetched directly. "Verbatim" quotes are marked; anywhere a WebFetch summarizer (not raw HTML) produced the text, that is noted. Two sources required a workaround: `code.claude.com` (Anthropic redirected its old anthropic.com/engineering URLs there — content fetched from the live destination) and `martinfowler.com` (403 to normal WebFetch/curl; reached via a Wayback CDX cross-reference to find the article slug, then a browser-UA `curl`).

## Method and verification legend

- **Direct fetch (raw)**: `gh api ... --jq .content | base64 -d` (exact file bytes) or a WebFetch that returned full page text rather than a condensed summary (Anthropic's best-practices/common-workflows pages, Devin's `.md` doc pages, Böckeler's article via curl, Kent Beck's Substack API archive, Mitchell Hashimoto's post via curl).

## Lens 1 — Vendors

### GitHub Spec Kit (`github/spec-kit`)
- Repo stats (`gh api repos/github/spec-kit`, live 2026-09-22): **138,339 stars, 12,394 forks, 307 open issues**, created 2025-08-21, pushed 2026-09-22 (same day — actively maintained).
- Workflow as currently documented (README, direct fetch): **constitution → specify → plan → tasks → implement → converge**, where "constitution" is a one-time project-level step and the rest repeats per feature. There's also a separate Bug-Fixing Workflow (assess → fix → test, with "Missing verification is not a successful fix" as an explicit design principle) and an Idea-Assessment Workflow (intake → research → define → shape → decide, outcomes go/needs-clarification/kill).
- Launch post (Den Delimarsky, Sept 2 2025, https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/) describes only **four** phases (Specify, Plan, Tasks, Implement) — no "constitution" step existed at launch; it was added later. Verbatim: "A vague prompt like 'add photo sharing to my app' forces the model to guess at potentially thousands of unstated requirements" vs. a spec giving the agent "more clarity, improving its overall efficacy." Three named use cases: greenfield, feature-work-in-existing-systems ("spec-driven development is most powerful" here), legacy modernization.
- **No numeric claims anywhere** — confirmed by a second, independent direct fetch of the raw README (`raw.githubusercontent.com/github/spec-kit/main/README.md`): "purely descriptive... no success-rate/quality numbers anywhere."
- **No explicit "skip for small tasks" carve-out** — this is the one vendor of five that does not state a task-size floor below which SDD shouldn't be used (see cross-vendor pattern below).
- Open-issue sample (30, direct fetch): complaints are about tooling/integration bugs (Forge dispatch args, opencode v2 incompatibility, release-archive fetch failures), not about the methodology's overhead. No "abandoned due to overhead" thread found in spec-kit's own tracker after a broad keyword sweep (overhead / too complex / abandoned / gave up — see Lens 2 §10 for the practitioner-side search).

### Amazon Kiro
- https://kiro.dev/docs/specs/ (direct, summarized): three artifacts — requirements.md, design.md, tasks.md — with automatic dependency-aware "wave" parallelization of independent tasks.
- https://kiro.dev/docs/specs/best-practices/ (direct, summarized) is the **most explicit task-size gating of any vendor**: it defines three spec types with selection criteria —
  - **Feature Spec**: "Complex features with multiple requirements needing iteration," "domain-sensitive projects where ambiguity is costly," "situations requiring team review and approval checkpoints."
  - **Quick Spec**: "you're working on a well-understood feature where you trust Kiro's output," or "rapid prototyping and want speed over review" — an explicitly lighter path for smaller work.
  - **Bugfix Spec**: for critical-path bugs, regressions from prior fixes, or non-obvious root causes.
  - Caveat: "you must choose a workflow when creating the spec. If you need to change approaches, create a new Feature Spec" — not mutable in place.
- Homepage framing (direct, summarized): positioned for "complex tasks" and "building on top of large codebases" — "implement more complex tasks in fewer shots" vs. vibe coding alone. One customer-testimonial quote ("weeks to days") explicitly flagged by the vendor as a customer quote, not a Kiro-measured metric.
- No AWS-domain blog post with case studies was reachable — `aws.amazon.com/blogs/aws/introducing-kiro/`, `.../blogs/devops/from-spec-to-code-kiro/`, and `.../blogs/devops/kiro-and-the-future-of-ai-assisted-development/` all returned **404**, confirmed directly (not guessed). Only the kiro.dev-domain announcement was reachable.

### Anthropic Claude Code best-practices — the exact quote requested
- `anthropic.com/engineering/claude-code-best-practices` now 308-redirects to `code.claude.com/docs/en/best-practices`; fetched the live destination directly, full text (not summarized).
- Recommended flow: **Explore → Plan → Implement → Commit**. Plan mode: `Shift+Tab` until "⏸ plan mode on," or `claude --permission-mode plan`.
- **Verbatim, exact wording**, in a callout box directly after the four-phase workflow:
  > "Plan mode is useful, but also adds overhead.
  > For tasks where the scope is clear and the fix is small (like fixing a typo, adding a log line, or renaming a variable) ask Claude to do it directly.
  > Planning is most useful when you're uncertain about the approach, when the change modifies multiple files, or when you're unfamiliar with the code being modified. If you could describe the diff in one sentence, skip the plan."
- Separately, a **"Let Claude interview you"** section is the document's own answer for larger features — explicitly scoped to "larger features," not small ones: "Start with a minimal prompt and ask Claude to interview you using the `AskUserQuestion` tool... Ask about technical implementation, UI/UX, edge cases, concerns, and tradeoffs... Keep interviewing until we've covered everything, then write a complete spec to `SPEC.md`." Then: "start a fresh session to execute it... The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step... Time spent making the spec precise pays off more than time spent watching the implementation."
- This is notable: **Anthropic's own guidance is a size-gated hybrid** — interview-then-SPEC.md for large/ambiguous features, direct execution for small/clear ones, plan-mode in between. It is structurally closer to "grill until it holds, then write a short artifact" than to GitHub Spec Kit's uniform multi-phase pipeline.
- `common-workflows` (redirects to `code.claude.com/docs/en/common-workflows`, direct fetch): also documents `/batch <instruction>` — splitting large migrations across 5–30 subagents in worktrees — a separate large-scale pattern, not spec-first.

### OpenAI Codex
- Repo stats (`gh api repos/openai/codex`): 125,921 stars, 19,598 forks, **18,268 open issues** — a far higher issue/star ratio than Spec Kit, actively maintained (pushed same day).
- Public docs site (`developers.openai.com/codex/cli/features` → `learn.chatgpt.com/docs/codex/cli`, summarized fetch): no dedicated plan-mode/spec-workflow page; framing is interactive/subagent-delegation, not document-first.
- **Strongest evidence for this vendor came from raw source, not docs** (`gh api .../contents/... --jq .content | base64 -d`, exact bytes):
  - `codex-rs/protocol/src/prompts/base_instructions/default.md`, "Planning" section: the `update_plan` tool is an in-session TODO/checklist, explicitly **not** a spec-writing phase. Verbatim skip condition: "Do not use plans for simple or single-step queries that you can just do or answer immediately."
  - `codex-rs/collaboration-mode-templates/templates/plan.md`, the actual "Plan Mode (Conversational)" system prompt — Codex's functional analog to Claude Code's plan mode / Spec Kit's specify+plan. Verbatim: "You work in 3 phases, and you should *chat your way* to a great plan before finalizing it... It must be **decision complete**, where the implementer does not need to make any decisions." Phase 2 explicitly: "Bias toward questions over guessing: if any high-impact ambiguity remains, do NOT plan yet — ask." Output is deliberately kept short: "3-5 short sections... Do not include a separate Scope section unless scope boundaries are genuinely important."
  - This "chat your way to a decision-complete plan by asking questions" phrasing is, on its face, close to the owner's "grilling" description — a chat-based interrogation that ends in a compact artifact, not a heavyweight multi-document spec.

### Cursor and Devin
- Cursor (`cursor.com/docs/agent/planning`, direct fetch): "Plan Mode creates detailed implementation plans before writing any code." Explicit use-list: complex features with multiple valid approaches, tasks touching many files/systems, unclear requirements, architectural decisions. Explicit skip condition (verbatim): **"For quick changes or tasks you've done many times before, jumping straight to Agent mode is fine."** Recovery guidance: if a plan-driven implementation goes wrong, "go back to the plan... revert... refine the plan," not patch forward.
- Devin (`docs.devin.ai`, direct fetch of `.md` pages): the most quantified task-size framing of any vendor — **"if a task would take you three hours or less, Devin can most likely do it"**, longer work should be split into sessions sized XS/S/M via "Session Insights." "Scope tasks with Ask Devin before implementation" for complex work. One customer-reported figure, explicitly flagged by the fetch as a self-reported customer claim, not an independent measurement: "8x human time savings" on a multi-million-line migration. Devin's docs do **not** prescribe a formal spec-file format (no requirements.md/design.md equivalent) — planning is recommended, but no document artifact is mandated.

### Cross-vendor pattern (flagged by the vendor-lens agent, load-bearing for this record)
Four of five vendors state an explicit, near-identical "skip planning for small/clear/routine work" condition (Anthropic's one-sentence-diff test, Codex's "simple or single-step" test, Cursor's "quick changes... jumping straight to Agent mode is fine," Devin's 3-hour/XS-S-M threshold, Kiro's "Quick Spec" path). **GitHub Spec Kit is the outlier**: its docs present SDD as broadly applicable across greenfield/feature/legacy-modernization work with no stated floor.

## Lens 2 — Practitioners

### Proponents
- **Den Delimarsky** (den.dev, https://den.dev/blog/github-spec-kit/, Oct 12 2025) — hedged pro-spec: "specs are not a panacea and certainly not yet anywhere near offering the ability to one-shot products," "Human in the loop is as important as it ever was." Task: a single moderate feature (34-camera snapshot aggregator), built in under two hours. He is closely associated with Spec Kit (co-wrote the GitHub launch post); no follow-up "reconsidering" post found on his blog.
- **Kiro/AWS team** — "Introducing Kiro" (Swaminathan & Singh, kiro.dev, Jul 14 2025): "Requirements are usually uncertain when you start building, which is why developers use specs for planning and clarity." "Requirements analysis" post (5 named AWS engineers, kiro.dev, May 12 2026) cites model-degradation numbers to motivate specs: **"Pass@1 drops of 20–40%, with 60–90% of the syntactically valid code being semantically wrong"** [unverified primary source for this figure — the kiro.dev post cites it, but the agent did not trace it to the underlying study; treat as a vendor-cited number, not independently confirmed here]. Task shape: medium-to-large full-stack features (review systems, order processing, auth) — explicitly "beyond vibe coding," not tiny fixes.
- **Tessl** (tessl.io) — a spec-first-adjacent startup ("context-driven agent factories"). Homepage numeric claims (marketing copy, not a methodology page — flagged as vendor claims requiring independent verification): "74% of findings are real defects... up from 50%," "94% task success, up from 67%." Blog contributors include Dave Farley ("Vibe Coding Is Not The Best We Can Do," Aug 24 2026, advocating "specification, verification, and tests").

### Practitioner-experience / nuanced (not forced into a camp) — the single richest source in this survey
- **Birgitta Böckeler**, martinfowler.com, "Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl" (https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html, Oct 15 2025). She hands-on tried all three tools and reports **task-size mismatch as her central, load-bearing finding**:
  - On Kiro for a small bug fix (verbatim): **"it quickly became clear that the workflow was like using a sledgehammer to crack a nut. The requirements document turned this small bug into 4 'user stories' with a total of 16 acceptance criteria."**
  - On Spec Kit for a "3-5 point story" (verbatim): **"this again felt like overkill for the size of the problem... I never even finished the full implementation, but I think in the same time it took me to run and review the spec-kit results I could have implemented the feature with 'plain' AI-assisted coding, and I would have felt much more in control." "To be honest, I'd rather review code than all these markdown files."**
  - General skepticism of upfront volume (verbatim): "The past has shown that the best way for us to stay in control of what we're building are small, iterative steps, so I'm very skeptical that lots of up-front spec design is a good idea, especially when it's overly verbose... small work packages almost seem counter to the idea of SDD."
  - She still affirms the general principle (verbatim): "In my personal usage of AI-assisted coding, I also often spend time on carefully crafting some form of spec first to give to the coding agent. So the general principle of spec-first is definitely valuable in many situations." Her critique targets the elaborate multi-document *tooling*, not spec-writing per se.
  - Closing line (verbatim), invoking the German word for "an attempted improvement that makes things worse": **"Are we making something worse in the attempt of making it better?"**
  - Her taxonomy — spec-first / spec-anchored / spec-as-source — is a useful vocabulary: "All SDD approaches and definitions I've found are spec-first, but not all strive to be spec-anchored or spec-as-source." She draws an explicit MDD (model-driven development) analogy: MDD "never took off for business applications, it sits at an awkward abstraction level and just creates too much overhead and constraints," and worries spec-as-source "might end up with the downsides of both MDD and LLMs: Inflexibility and non-determinism."

- **Simon Willison** — **not found**: no essay using the term "spec-driven development"; site search for "spec-driven"/"spec kit" returned 0 relevant hits, dedicated tag pages don't exist (404). - **Thorsten Ball** — **not found** on SDD specifically; one Sep 19 2026 futurist post has an adjacent line ("Most bugs won't be 'coding' bugs. They'll be 'you asked for the wrong thing' bugs") but the same post predicts "Agile, SCRUM, whatever – dead," i.e., an expectation that process/ceremony gets swept away rather than formalized — flagged as inference, not his stated position on SDD.

This is a genuine negative result (the search API returned real matches for every query, just none on-topic), not a search failure. The closest hit is a documentation-gap complaint (#1118: Spec Kit's docs cover greenfield well but not applying it to an existing project) — friction, not abandonment. (See Lens 4 for actual removal *commits*, which is a stronger and more concrete signal than issue-tracker narration.)

### Cross-cutting practitioner observation
Böckeler's task-size finding (sledgehammer-to-crack-a-nut below "3-5 points") and Kent Beck's independent, unrelated minimal-context practice converge on the same conclusion from opposite directions: match plan/spec weight to task size, and default toward less upfront documentation, not more. The pro-spec camp (Delimarsky, Kiro's own team, GitHub's own framing as quoted by Böckeler) does not really disagree on this axis — they scope specs to "medium-to-large," "production," or "uncertain requirements" work; they draw the size threshold differently, not the principle.

## Lens 3 — Measured evidence

**Distinguishing (A) planning inside the agent's own loop** (an in-session TODO/plan the agent itself writes and follows) **from (B) human-authored spec documents written before implementation** (Spec Kit / Kiro style) is essential — most controlled coding-agent evidence is (A), not (B).

### Category A — in-loop planning ablations (coding-specific)
- **"From Plan to Action: How Well Do Agents Follow the Plan?"** (Liu, Dehghan, Ganhotra, Hirzel, Jabbarvand; ASE 2026) — https://arxiv.org/abs/2604.12147. 21,120 trajectories, 4 models, SWE-bench Verified + Pro, 8 plan-scaffold settings. Finding (quoted): "The success rate drops in the absence of the standard plan, although to different degrees across models" — DeepSeek models show "a substantial performance drop," Devstral-small/GPT-5-mini "only minor drops." Success rates under the standard-plan setting: GPT-5-mini 56.3%, DeepSeek-V3 38.4%, DeepSeek-R1 39.4%, Devstral-small 64.8%. This is category A: a scaffold-level plan baked into the agent's system prompt, not a human-written spec document.
- **"LivePlan"** — https://arxiv.org/abs/2608.06701 — real-time plan-drift correction on SWE-bench Verified/Pro: "consistent gains of up to 15.2% (average: 9.9%)" resolve rate vs. vanilla SWE-agent, +$0.08/instance cost. Category A.
- **"SWE-Edit"** — https://arxiv.org/abs/2604.26102 — plan/execute subagent split: "+2.1pp resolve rate, -17.9% inference cost." Category A.

### Category B — human-authored spec-document studies (much thinner evidence base)
- **"OpenHarmony Bench"** — https://arxiv.org/abs/2608.16022 — the single strongest **negative, controlled, quantitative** finding in this survey for spec-first task framing specifically: comparing spec-driven (50 tasks), new-feature/NL (32 tasks), and bug-fix (71 tasks) inputs across 8 LLMs × DevEco Code × 3 runs, **"spec-driven tasks have the lowest Task Completion under all-checks task scoring, with no configuration exceeding 35%,"** despite build-success rates of 94.77–100%. I.e., structured upfront specs produced code that *built* but did not *behave correctly* more often than natural-language requests did, in this benchmark. This directly contradicts the vendor framing that specs reduce ambiguity-driven failure — worth weighting heavily as a counterpoint, while noting it is one benchmark, one toolchain (mobile ArkTS/DevEco), not a general result.
- **"Citation Discipline in Spec-Driven Development"** — https://arxiv.org/abs/2606.30689 — compares three real spec frameworks (traceSDD, GitHub Spec Kit, OpenSpec) against each other, not against a no-spec baseline (N=20 Claude Sonnet 4.6 / N=50 GLM-5-turbo, 240/600 implementations). Finding: citing sources in the spec produces significantly *higher* determinism than not citing (Claude d=-0.76 p=0.003; GLM d=-0.72 p<0.001); traceSDD beats Spec Kit on determinism (Claude d=0.47 p=0.049) but not OpenSpec. Useful only for "which SDD flavor," not "SDD vs. none."
- **"SpecMine"** (corpus study) — https://arxiv.org/abs/2608.25202 — 470,795 spec.md-style files across 73,030 repos (17 tools), a Kiro-specific census of 98,574 files/12,910 repos, and 5,992 spec-touching PRs across 581 repos. This is the dataset that *would* let someone measure spec-code drift — the paper does not itself report a drift percentage.
- Two n=1 anecdotal case studies exist with striking numbers (90% first-review acceptance / 85% staffing-cost reduction in one; 73% security-defect reduction in another) — both explicitly flagged by the measured-evidence agent as single-case, no control group, self-reported; not weighted as evidence here.
- One paper explicitly names the evidence gap itself: "Spec-Driven Development for Agentic Software Engineering" (https://arxiv.org/abs/2609.00252) states its method is "conceptual analysis drawing predominantly on gray literature... because peer-reviewed evidence and a shared academic-industrial vocabulary are not yet established."

### Explicitly "no numbers found"
- **METR** (metr.org/blog, metr.org/research, both checked directly): confirmed no post ablates spec/plan-first workflows. Their well-known "time horizon" capability trend is a different question entirely and must not be cited as SDD evidence.
- **Anthropic engineering blog**: the closest-titled article ("Effective harnesses for long-running agents") describes a human-authored spec artifact produced by an "initializer agent" but gives **no quantitative comparison** for it vs. not using one.
- **OpenAI cookbook**: returned HTTP 403 this session — unverified, not "no numbers," genuinely inaccessible.
- **GitHub Spec Kit and Kiro's own docs**: confirmed, by direct fetch, to contain **zero** quantitative success-rate claims — both vendors' primary documentation is entirely qualitative/descriptive on this point (a finding in itself: the two most-adopted SDD tools do not publish numbers backing their own approach).
- **Spec-drift/maintenance-cost rate**: no measured percentage found anywhere. One paper built the dataset (SpecMine, above) but hasn't computed it; one other paper ("Specification-delta-driven data governance," https://arxiv.org/abs/2608.19838) designed a controlled experiment to measure it but explicitly has not yet run it.

## Lens 4 — In the wild (GitHub adoption, all via `gh`, live 2026-09-22)

- **Spec Kit adoption signal**: `gh api search/code -f q="path:.specify" --jq .total_count` → **94,080** (GitHub's code-search `total_count` is index-approximate, not an exact repo count — full pagination for a precise dedup hit a secondary rate limit after ~2 pages; reported honestly as directional, not precise).
- **Kiro adoption signal**: `path:.kiro/specs` → **154,368** (same approximation caveat).
- **Spec Kit repo health**: 138,339 stars / 12,394 forks / 307 open issues, pushed same day as this research (actively maintained upstream).
- **Fork-divergence spot-check** (a proxy for "forked to actually use, not just to look at"): sampling both newest forks (hours old) and oldest forks (~1 year old) of `github/spec-kit` found the newest 4 sampled forks had **zero commits** (404 on `/commits` despite the repo existing — clone-and-abandon), and most of the oldest sampled forks showed only upstream merge-pull commits, no genuine divergent work. One exception (`chanezon/spec-kit`) had a real CLI-rename commit. **Pattern: forks are overwhelmingly passive/dormant copies, not active independent development** — a caution against reading the 12,394 fork count as 12,394 active users.
- **Issue-tracker complaint search** (overhead / too complex / abandoned / gave up / too much overhead): no direct "this is too much overhead, we stopped" thread found in Spec Kit's own tracker — a genuine 0-results finding, not a blocked search.
- **Removal/abandonment commits** — this is the strongest concrete "tried and stopped" signal found anywhere in this survey, because it is behavior, not narration:
  - `elastic/cli` — **"chore: drop spec-kit artifacts in favor of AGENTS.md (#247)"** — an official Elastic repo explicitly rejecting Spec Kit's convention for the generic AGENTS.md convention.
  - `quickstart-now/hejbro` — **"revert(process): drop spec kit adoption (undo #285) (#292)"** — adopted, then explicitly reverted.
  - `wasikarn/devflow` — "drop spec-kit suite — superseded by team-dev-loop + Jira" — replaced by a custom workflow plus an existing PM tool.
  - Also found: `LukeCarrier/dotfiles` (2 separate "drop spec-kit" commits across machine profiles), `Pakrohk-DotFiles/ziro-shell`, `PlagaMedicum/wiki-scripts`, `Yekuuun/Mango` ("drop Spec Kit scaffolding, add Claude Code hooks" — replaced by a different harness), `richelgomez99/founder-s-orchestrator` ("drop spec-kit scaffolding... for showcase" — implies spec-kit artifacts were seen as dev-only clutter not worth showing).
  - `gh search commits "remove spec-kit"` (without hyphen-normalization) hit a secondary rate limit mid-run — reported as **"search blocked, result unknown,"** not folded into the 0/N counts above.
- **Spec-drift proxy** (5 real repos, last commit touching the spec dir vs. last commit touching the general codebase): in every one of the 5 sampled repos, code commits continued *after* (or at best same-day as) the last spec-directory commit — **no case showed a spec being updated after the related code changed**. The clearest drift case, `ambient-code/platform`: spec last touched 2026-05-28, general development continued to 2026-09-03 — a **98-day gap** with no spec update. Two repos (`delphicleancode/delphi-spec-kit`) simply died 2 days after creation (looked like a spec-kit demo repo, not sustained real use).
- **Kiro adoption quality**: of 6 `.kiro/specs` repos spot-checked for authenticity, most were genuine actively-maintained projects (sebsto/wispr — 157★, releases through Sep 2026; soc221b/zod-schema-faker — established since 2022, Renovate-bot-maintained; izumin5210/gqlkit — 31★, active) but the sample also included a confirmed tutorial repo (`yoshidashingo/getting-started-with-kiro` — description null, commits are "最新化"/README-date-bumps) and a short-lived abandoned repo (11-day burst then nothing) — **the raw code-search hit counts for both `.specify` and `.kiro/specs` are inflated by tutorial/demo repos and dormant forks**, so the 94k/154k figures should not be read as "94k/154k teams using SDD in production."

## Explicit comparison: spec-document-first vs. grill-then-decide (short decision records)

Nothing in this survey found a controlled study pitting "author a spec/plan/tasks document up front" against "interrogate the design conversationally, then write a short decision record (ADR/MADR-style)" as two named alternative practices — that specific comparison does not appear to have been studied empirically anywhere found (mark as **no precedent found**, not "the hybrid wins"). What the four lenses *do* support, convergently:

1. **The vendors themselves are already hybrid, not uniform-SDD.** Four of five vendors (Anthropic, Codex, Cursor, Devin) gate planning explicitly by task size and default to direct/minimal-ceremony execution for small or well-understood work — only GitHub Spec Kit presents SDD as broadly applicable with no stated floor. Anthropic's own "Let Claude interview you... then write a complete spec to SPEC.md" for *large* features, combined with "if you could describe the diff in one sentence, skip the plan" for small ones, is structurally a size-gated hybrid — much closer to "grill for big things, nothing for small things" than to Spec Kit's uniform pipeline. Codex's Plan Mode template is explicitly conversational-interrogative ("chat your way to a decision-complete plan," "bias toward questions over guessing") before it ever produces a document, and the document it produces is deliberately short (3–5 sections).
2. **The strongest practitioner account (Böckeler) is a direct, hands-on critique of the heavyweight multi-document form specifically**, not of spec-writing as a principle: she affirms "the general principle of spec-first is definitely valuable" while reporting that Kiro/Spec-Kit's *volume* of generated artifacts (16 acceptance criteria for a small bug; markdown files she'd rather not review) made her feel *less* in control, not more, below roughly a 3–5-point-story size. This maps closely onto "short decision records over long spec documents" as the size-appropriate alternative, though she never uses the ADR/MADR term herself.
3. **Kent Beck's independent, unrelated practice converges on the same shape from a different angle**: minimal standing context, narrow per-step instructions, outcome-described rather than plan-engineered — closer to "grill this step, then move" than to comprehensive upfront specification.
4. **The one controlled, negative, quantitative result specific to human-authored specs (OpenHarmony Bench)** found spec-driven task framing performed *worse* on behavioral correctness than natural-language requests, despite building successfully — a data point against assuming more upfront structure reliably improves agent output, though it is one benchmark on one mobile toolchain and should not be over-generalized.
5. **The "in the wild" removal-commit evidence (elastic/cli, quickstart-now/hejbro, wasikarn/devflow, and others) is concrete behavioral evidence of teams adopting Spec Kit and then discarding it**, in at least two cases explicitly in favor of a lighter alternative (AGENTS.md; a custom dev-loop). This is a small, non-random sample (found via commit-message keyword search, not a census) but it is real, not narrated.
6. No source in any lens directly evaluated "decision records instead of specs" as a named practice with outcome data. If the owner wants to close this specific gap empirically, it would require either a first-party trial (their own repos, before/after) or a wait for someone else to run it — nothing found here substitutes for that.

## Plain-language verdict

SDD-as-a-uniform-methodology (GitHub Spec Kit's framing: every feature gets constitution→specify→plan→tasks→implement) is not well supported as a universal default in 2026. The evidence that exists — vendor guidance, the most detailed hands-on practitioner account, and the one controlled negative benchmark — converges on the same shape: **match the weight of upfront structure to the size and ambiguity of the task, and default toward less ceremony, not more.** Four of the five vendors surveyed (Anthropic, OpenAI Codex, Cursor, Devin) already build this gating into their own tools and explicitly warn that planning "adds overhead" for small, clear-scope work; only GitHub's own Spec Kit is a genuine outlier in prescribing SDD broadly. The strongest independent practitioner account (Böckeler) tried Kiro and Spec Kit hands-on and found both to be overkill below roughly a 3–5-point-story size — while still affirming that some form of spec-first thinking is valuable for bigger, more uncertain work. GitHub-search evidence of teams adopting and then explicitly discarding Spec Kit in favor of lighter conventions (AGENTS.md, custom decision logs) exists, though it is a small non-random sample of found commits, not a census.

Controlled, quantitative evidence *specific to human-authored spec documents* (as opposed to an agent's own in-loop planning step, which is much better studied and does generally help) is thin — one negative benchmark (OpenHarmony Bench), one within-SDD-flavor comparison, and a scattering of n=1 case studies on both sides. Nobody has directly measured "spec doc first" against "grill-then-record" as two named competing practices. That specific claim — that grilling-to-a-short-decision-record beats spec-authoring for the owner's typical task sizes — is not something this survey can confirm or refute with numbers; it is, however, consistent with (a) what four of five vendors' own size-gating logic implies, (b) the one detailed hands-on trial report available, and (c) the one controlled negative result on spec-driven task framing. The honest reading is: **keep `sdd` for genuinely large/ambiguous/multi-file work (which is roughly what Anthropic's own SPEC.md guidance, Kiro's "Feature Spec" criteria, and Böckeler's size threshold all independently point to), and treat "grilling + a short decision record" as the better default for everything smaller** — which is close to a hybrid every major vendor except GitHub already ships, not a fringe position.
