# Coding agents inside a "box": how vendors and tools handle the mechanics (2026-09-22)

Research question: when a coding agent (Claude Code, Codex, pi, DSH, any CLI agent) runs inside an isolated environment (container, microVM, cloud sandbox), how do vendors and the main tools handle (1) repo into the box, (2) config/skills/credentials into the box, (3) work out of the box, (4) resume inside the box, (5) network policy and host tools such as `gh`/`gcloud`, (6) the harness's own sandbox nested inside the outer box.

Method and notation
- Sources were fetched directly (docs pages, `gh api` for repo files) by four parallel research lanes plus a first-hand inspection of the locally installed `sbx` v0.43.0 binary and CLI help. Web search quota was exhausted mid-run, so a few sub-pages could not be located; those are marked "not documented (not located)".
- Quotes in "double quotes" are verbatim from the cited URL. `[binary-observed sbx v0.43.0]` marks strings and embedded kit specs read out of the local `sbx` executable (first-hand, but not a documented promise). `[local-observation 2026-08-15]` marks facts recorded in the owner's own earlier sbx integration notes (older sbx version; may have changed). `[unverified]` marks inference.
- Nothing below assumes any design is right. Where vendors disagree, both positions are recorded.
- Vendor URL note: `developers.openai.com/codex/*` now 308-redirects to `learn.chatgpt.com/docs/*` (observed 2026-09-22). Both are cited.

## 1. Docker Sandboxes (`sbx`, v0.43.0) — the tool the owner uses

Primary sources: https://docs.docker.com/ai/sandboxes/ (sub-pages: `/architecture/`, `/security`, `/workflows`, `/configuration`, `/usage/`, `/agents`, `/customize`, `/troubleshooting/`, `/faq`, `/governance`), CLI reference https://docs.docker.com/reference/cli/sbx/ , local `sbx --help` output, and the built-in agent kit specs embedded in the binary.

Overview page (https://docs.docker.com/ai/sandboxes/): each sandbox is a "Dedicated microVM with separate Docker daemon, filesystem, and network"; "The agent cannot reach host resources unless explicitly shared"; "Centrally managed credential handling within the sandbox"; "Upstream proxy configuration available for network policies". The CLI is free; "organization governance requires a separate paid subscription".

Anthropic's own docs name Docker Sandboxes as a VM-class option: "Docker Sandboxes provides a microVM with its own Docker daemon and workspace sync, which can run Claude Code on any host with Docker Sandboxes installed. It is a free, standalone product from Docker that does not require Docker Desktop." (https://code.claude.com/docs/en/sandbox-environments)

### 1.1 Repo into the box

Two documented modes, chosen at creation time.

Bind mount (default). `sbx run claude` / `sbx create claude .`: "Omit the path to mount the current directory. Pass a path to mount a different workspace." Extra workspaces can be appended and made read-only: "Additional workspaces can be provided as extra arguments. Append ':ro' to mount them read-only; a read-only argument may name a single file, which holds that one path out of reach inside a workspace the sandbox can otherwise write." (`sbx run --help`, v0.43.0). `sbx create` without a path: "Omit the path to create a sandbox without a workspace bind mount: the agent then works in the container's own filesystem instead of on your files." The MCP tool description in the binary says the same: "Mounts the given workspace directory, or provisions a new empty one under ~/.sbx/workspaces when omitted." [binary-observed sbx v0.43.0]. The in-container path equals the host path on macOS/Linux — the built-in cursor kit comments: "WORKSPACE_DIR (the in-container workspace path, which equals the host path on macOS/Linux bind mounts)" [binary-observed sbx v0.43.0]. The filesystem is virtiofs (binary string "virtiofs caching: disabled for path") [binary-observed].

Clone mode (`--clone`). Flag text, verbatim: "Run the agent on a private in-container clone of the host Git repository (mounted read-only) instead of bind-mounting the workspace; the agent's commits are accessible via the sandbox-<name> git remote on the host" and "must be set at sandbox creation time (no-op when re-attaching to an existing clone-mode sandbox)" (`sbx create --help`, `sbx run --help`). Example: "# Run the agent on an in-container clone of the host repo, wired back via a git-daemon / sbx create --clone claude ." Binary strings show the host repo is mounted at `/run/sandbox/source` and the clone's `origin` points there: "clone-mode: could not list host remotes for propagation; in-container clone will only have origin -> /run/sandbox/source" [binary-observed]. So the clone normally also inherits the host's other remotes (propagation). Kit files that target the clone directory are unsupported: "the following kit initFiles target the in-container clone directory, which is unsupported in --clone mode: Move these into files/workspace/<path> in the kit — workspace files write reliably after the clone" [binary-observed].

Documented semantics and trade-offs (https://docs.docker.com/ai/sandboxes/architecture/ , https://docs.docker.com/ai/sandboxes/workflows/git/ , https://docs.docker.com/ai/sandboxes/security/isolation/): "A directly mounted workspace appears at the same absolute path as on your host"; "Virtiofs caching is enabled by default for directly mounted workspaces on all operating systems" (disable with `DOCKER_SANDBOXES_ENABLE_VIRTIOFS_CACHE=0`); mountless sandboxes use the image WORKDIR, "typically `/home/agent/workspace`". Clone mode: "Clone mode creates a separate Git clone inside the sandbox. The agent edits this clone instead of your host working tree. Its changes stay inside the sandbox until you fetch a branch or the agent pushes one to a remote." "Your repository is mounted read-only into the VM and the agent works on a private clone inside the VM. The agent's edits never reach your host until you fetch them." Clone mode "protects your host repository from modification, not from inspection". The vendor's own trade-off summary: direct mode = "immediate visibility, no parallelism, you manage branches"; clone mode = "branch isolation, multiple parallel agents possible, changes isolated until fetched". Troubleshooting (https://docs.docker.com/ai/sandboxes/troubleshooting/): in direct mode `git status`/`git log`/directory scans "can be noticeably slow" on large repos; workspace mount configuration is fixed at creation time.

Worktrees (host-side git worktrees as the workspace). Documented as an alternative to `--clone` with a hard limitation (workflows/git): "because the sandbox mounts only the worktree directory (not the parent repository), it can't resolve the .git pointer file and has no Git access. The agent can read and write files, but can't commit, branch, or check status." Issues: #154 (closed) — the agent "can still access uncommitted and secret files from the host checkout by traversing parent directories" (https://github.com/docker/sbx-releases/issues/154); #101 (open) "sbx removes git worktrees in .sbx/ without warning when sandbox is removed" (https://github.com/docker/sbx-releases/issues/101); #432 (open) "Placement of AGENTS.md / CLAUDE.md files don't work with standard worktree workflows" (https://github.com/docker/sbx-releases/issues/432). The binary carries labels `com.docker.sandbox.usesWorktree` / `com.docker.sandbox.worktreePath` and "failed to remove sandbox worktree directory %s" [binary-observed]; whether clone mode itself is implemented with a staging worktree is [unverified].

Clone-mode bugs on the tracker (https://github.com/docker/sbx-releases — the docker/sandboxes repo does not exist): #460 (open) "`--clone` mode fails silently (empty workspace) when the source repo is a shallow git clone" (v0.43.0 notes say clone mode "now support[s] shallow Git repositories"); #491 (open) "`--clone` does not work in WSL when creating new sandboxes"; #354 (closed) "Claude by-passed read-only limitation when working in --clone mode" (agent edited the read-only host mount instead of the private clone).

Stated trade-off of clone mode [local-observation 2026-08-15]: "`--clone` stops destruction, not disclosure. The working tree holds only tracked files, but `/run/sandbox/source` mounts everything read-only, so `cat /run/sandbox/source/.env` works. Only the network policy stops exfiltration."

`sbx env` (experimental) manages sandboxes from an `sbxenv.yaml`; the workspace object accepts exactly `path` and/or `clone` ("workspace: unknown field %q (expected 'path' and/or 'clone')") [binary-observed].

### 1.2 Config / skills / credentials into the box

Credentials are proxy-injected, not copied. `sbx secret --help`: "When a sandbox starts, the proxy uses stored secrets to authenticate API requests on behalf of the agent. The secret is never exposed directly. Scoped globally (shared across all sandboxes) or to a specific sandbox." Registry secrets "are not injected into sandboxes unless --all-sandboxes or --sandbox is set (the credential never enters the sandbox filesystem)."

The built-in `claude` kit (embedded in the binary, `schemaVersion: "2"`, `kind: sandbox`) [binary-observed sbx v0.43.0] shows the exact mechanics:
- Entry point: `entrypoint: [claude, "--dangerously-skip-permissions"]`.
- Credentials: an `apiKey` inject rule (`x-api-key` header added by the proxy for `api.anthropic.com`, `console.anthropic.com`, `claude.ai`, `mcp-proxy.anthropic.com`) plus an OAuth block with sentinels `sk-ant-oat01-proxy-managed` / `sk-ant-ort01-proxy-managed` and a `credentialFile` template written to `~/.claude/.credentials.json`. The kit seeds `~/.claude/settings.json` with `"apiKeyHelper": "echo proxy-managed"` when a credential is present, `"permissions": { "defaultMode": "bypassPermissions" }`, `"bypassPermissionsModeAccepted": true`, `"skipDangerousModePermissionPrompt": true`, and seeds `~/.claude.json` with `hasCompletedOnboarding`, `bypassPermissionsModeAccepted`, and per-workspace `hasTrustDialogAccepted`. Comment in the kit: "settings.json is engine-managed and rewritten unconditionally on every (re)create".
- Env: `IS_SANDBOX: "1"`, `CLAUDE_ENV_FILE=/etc/sandbox-persistent.sh` (from the kit's injected CLAUDE.md agent instructions).
- MCP: `claude mcp add mcp-gateway "$MCP_GATEWAY_URL" --transport http --scope user --header "Authorization: Bearer $MCP_SENTINEL_TOKEN_NAME"` — "The sentinel name is not a credential — the proxy substitutes the real token at request time keyed by this name."
- The `codex` kit writes `~/.codex/config.toml` with `approval_policy = "never"`, `sandbox_mode = "danger-full-access"` ("This configuration enables 'yolo mode' - no approvals, full access"), `GIT_TERMINAL_PROMPT: "0"`, and in OAuth mode `model_provider = "sandboxd"` with `base_url = "https://chatgpt.com/backend-api/codex"` and `experimental_bearer_token = "oai-oat01-proxy-managed"`. Entry point: `[codex, "--dangerously-bypass-approvals-and-sandbox"]`.
- The `gemini` kit sets `GEMINI_SANDBOX: "false"`, `SANDBOX: docker`, entrypoint `[gemini, "--yolo"]`, and seeds `settings.json` with `"tools": {"sandbox": false}`, `"security": {"disableYoloMode": false, "folderTrust": {"enabled": false}}`.
- The `cursor` kit: `[cursor-agent, "--yolo"]`, `AGENT_CLI_CREDENTIAL_STORE: "memory"`; `devin`: `["--permission-mode", "dangerous", "--respect-workspace-trust=false"]`; `opencode`: `--dangerously-skip-permissions` [binary-observed].

Codex login inside the box is not persisted to the host: "Or, inside the sandbox, run `codex login` and choose the device-code flow. That login is not saved to the host credential store — it stays in that sandbox, so every new codex sandbox starts logged-out again." [binary-observed]. Claude subscription OAuth (`/login` inside the box) works without an API key [local-observation 2026-08-15]; the kit comment above ("without it Claude Code prompts for /login") is consistent.

Skills: a host-side shared store, mounted into the agent's skills directory. `--skills string`: "Shared skills store mode: off, readonly, or readwrite (mounted at the agent's skills directory, e.g. ~/.claude/skills). Default: readonly, or the configured skills.defaultMode setting. Can only be used when creating a new sandbox." `sbx skills --help`: "Skills are shared across sandboxes by default, mounted read-only." Store path on macOS: `~/Library/Application Support/com.docker.sandboxes/sandboxes/agent-skills` (`sbx skills ls`). Trade-off recorded by the owner [local-observation 2026-08-15, when the default was read-write]: a mount at `~/.claude/skills` cannot be replaced by a symlink manager ("Device or resource busy") and a read-write store is a cross-sandbox write channel.

Environment: `-e KEY=VALUE` or bare `KEY` "to take the value from the current environment"; `--env-file`; both "Applies to the agent session, so it takes effect on a re-attach too; also baked into the sandbox when this run creates it" (`sbx run --help`). `sbx setup` (experimental) imports detected agent secrets from host env vars and can enable SSH-agent forwarding ("When SSH_AUTH_SOCK is set, setup can enable SSH-agent forwarding and either use each client's current socket or persist a fixed socket path").

Kits: "Kits are declarative YAML artifacts that define sandbox agents or extend them with additional credentials, network policies, environment variables, startup commands, and files." (`sbx kit --help`). Mixins are added with `--kit ./dir` (directory, ZIP, git, OCI). Kit schema facts [local-observation 2026-08-15]: file must be `spec.yaml`, `schemaVersion: "2"`, `kind: mixin`.

Whole-`~/.claude` mounting is deliberately avoided by the vendor kit: "We mount subdirectories (not all of ~/.claude/) so kit-managed files like settings.json and .credentials.json continue to come from the image / oauth hook on every create." [binary-observed]

Host user-level config is explicitly NOT imported. FAQ (https://docs.docker.com/ai/sandboxes/faq/ , "Why doesn't the sandbox use my user-level agent configuration?"): "Sandboxes don't import your complete user-level agent configuration. Hooks, settings, and other files under directories such as ~/.claude remain on the host. Project-level configuration in the working directory remains available inside the sandbox... Don't use symlinks to host paths because a sandboxed agent can't follow them outside the sandbox." Codex page (https://docs.docker.com/ai/sandboxes/agents/codex/): "Sandboxes don't pick up user-level configuration from your host, such as ~/.codex." Issue #113 (open, https://github.com/docker/sbx-releases/issues/113): "the sandbox doesn't pick up ~/.claude (skills, agents, hooks, commands, settings.json, CLAUDE.md). The FAQ tells me to copy what I need into each project. That's not a viable answer... Bind-mount ~/.claude — sbx run claude . ~/.claude:ro mounts the directory, but at the host's absolute path. The sandbox agent runs as a different user (/home/agent), so Claude Code never sees it. There's no host:container remapping." Related: #446 (common `~/.claude/CLAUDE.md` request), #67 "OAuth credentials injection ignores CLAUDE_CONFIG_DIR, causing 401 when Claude Code uses a custom config dir."

Credential proxy, documented (https://docs.docker.com/ai/sandboxes/configuration/credentials/ , https://docs.docker.com/ai/sandboxes/security/): "An HTTP/HTTPS proxy on your host intercepts outbound requests from the sandbox, looks up the matching credential on the host, and overwrites the auth header before forwarding. The real credential stays on the host when proxy management is active; the sandbox sees only a sentinel value." "The host-side proxy injects authentication headers into outbound HTTP requests. The raw credential values never enter the VM." Built-in services: anthropic, copilot, cursor, devin, droid, github, google, groq, mistral, nebius, openai, openrouter, xai. Secrets live in the OS keystore (Keychain / Credential Manager / Secret Service, file fallback `~/.config/com.docker.sandboxes`). Dynamic sources: `--ref` (`op://...` or an AWS Secrets Manager ARN; needs `op`/`aws` on the host) or `--command`; cache 55 min, `--refresh on-demand`. Custom secrets: `sbx secret set-custom --host <domain> --env <VAR> ...` — "Inside the sandbox, API_KEY is set to a generated placeholder (e.g. sbx-cs-<rand>). When a sandboxed process sends a request to any of the configured hosts and the placeholder appears anywhere in the request, the proxy replaces it with the real value." Third-party kits must have their credential bindings approved in `~/.config/sbx/credentials.yaml` (`bindings: github: apiKey: domains: [api.github.com, github.com]`). Regression: #601 (open, v0.43.0) "Custom-secret substitution silently stops working in 0.43.0", attributed to the release-note item "Hardened credential handling in the sandbox egress proxy so a client-supplied credential the proxy did not issue is not forwarded to managed provider hosts" (https://github.com/docker/sbx-releases/issues/601). Kits are labelled experimental: "Kits are experimental. The kit file format, CLI commands, and experience... are subject to change" (https://docs.docker.com/ai/sandboxes/customize/kits/). Kit static files: `files/home/` → `/home/agent/`, `files/workspace/` → workspace.

### 1.3 Work out of the box

- Bind mode: edits land directly in the host tree (no export step).
- Clone mode: "the agent's commits are accessible via the sandbox-<name> git remote on the host" (flag help). Documented flow (https://docs.docker.com/ai/sandboxes/workflows/git/): `git fetch sandbox-<name>`, inspect `sandbox-<name>/feat/my-feature`, then merge/push to origin. "The Git daemon that exposes the in-sandbox clone runs as part of the sandbox. It's only reachable while the sandbox is running." A restart reassigns an ephemeral port and the CLI updates the `sandbox-<name>` remote URL in the host repo config; `sbx rm` removes "the sandbox, the daemon, the published port, and the sandbox-<name> remote entry." (The owner's 2026-08-15 note "No remote is auto-added on the host" predates this behaviour or contradicts it — the current docs say the remote is managed; the port still changes per start, so it must not be cached.) The daemon is fetch-only: issue #367 (open) "if I add a commit locally and try to push it back, I get 'fatal: remote error: access denied or repository not exported'" (https://github.com/docker/sbx-releases/issues/367).
- `sbx cp`: "Either SRC or DST must be a sandbox path, written as SANDBOX:PATH. The other must be a local path. Copying between two sandboxes is not supported." (https://docs.docker.com/reference/cli/sbx/cp/)
- PRs: general guidance only — create PRs via `gh pr create` after fetching, or have the agent push; the `github` service secret makes `gh` work through the proxy (see 1.5). "SSH agent forwarding is enabled by default" (workflows/git), so `git push` over SSH uses the host agent rather than the proxy.

### 1.4 Resume / continuation

- Re-attach by name: "To re-attach to an existing sandbox by name, use --name; the agent positional is optional when the named sandbox already exists and is read from its spec." Example: `sbx run claude -- --continue`.
- Conversation history is persisted by named block volumes declared in the kit, keyed to the sandbox name: "Volumes persist across container recreation. With deterministic volume naming, the same sandbox name reattaches to the same volumes on recreate — claude's session state survives `sbx kit add` and other recreate-shaped operations." Volumes: `/home/agent/.claude/projects` (2g, "Conversation history — the actual session content (~/.claude/projects/<workspace-as-dashes>/<session-id>.jsonl)"), `/home/agent/.claude/sessions` (512m, "Load-bearing for `claude -c` — without it the resume flag has no way to map 'the previous session' back to the matching transcript file"), `/home/agent/.claude/todos`, `/home/agent/.claude/shell-snapshots`, `/home/agent/.claude/statsig` [binary-observed sbx v0.43.0]. A volume left by a previous sandbox of the same name blocks reuse: "volume %q left by a previous sandbox of this name is still in use and cannot be removed; use a different sandbox name" [binary-observed].
- `sbx stop` "Stop one or more sandboxes without removing them"; `sbx prune` removes stopped sandboxes; cloud `--on-timeout stop` "stops it in place so it can be started again later". Cloud persistent volumes: `sbx volume` "(cloud-only)", `-v NAME:MOUNTPATH`.
- Documented persistence (https://docs.docker.com/ai/sandboxes/usage/): "Sandboxes persist after the agent exits. Running the same workspace path again reconnects to the existing sandbox rather than creating another sandbox." "While a sandbox exists, installed packages, Docker images, configuration changes, command history, and mountless workspace files all persist across stops and restarts." `sbx rm`: "everything inside is deleted. Host workspace files, including repositories used as clone sources, and the shared agent skills store remain on your host." So conversation history is box-local (the kit volumes above), survives stop/start and kit-add recreation, and is destroyed by `sbx rm`; the host's `~/.claude/projects` is never mounted. Conversation-history persistence is not called out in the docs themselves — the evidence is the kit spec [binary-observed] plus the `-- --continue` example in `sbx run --help`. Lifecycle bugs: #413 (closed) "Active sandbox was removed unprompted after computer was asleep"; #450 (open) "Auto-stop racing an incoming start request leaves a single sandbox permanently unstartable" (https://github.com/docker/sbx-releases/issues/450).

### 1.5 Network policy

- Global policy initialised once: `sbx policy init <allow-all|balanced|deny-all>`; "balanced — Typical development traffic is allowed, such as AI services and package registries"; "Per-sandbox rules, including those added by kits such as the built-in agent kits, apply on top for individual sandboxes." "If a resource matches both an allow and a deny rule, the deny rule takes precedence." `--deny-network` at creation: "Safe under centralized governance because a local deny can only narrow, never widen, egress." The local machine's policy currently reports "network: 193 allow" under balanced (`sbx policy ls`), consistent with the owner's note that balanced "already allows 192 domains, including every package registry and **.github.com" [local-observation 2026-08-15].
- Enforcement is a proxy in the VM gateway, with L7/MITM handling: binary strings "created proxy listener on gateway", "proxy: httpshandler mitm for l7 enforcement", "proxy: httpshandler mitm for host", "upstream proxy configured via PAC", "integrated proxy authentication (NTLM/Kerberos) is only supported on Windows" [binary-observed]. The credential injection described in 1.2 (adding `x-api-key` / `Authorization` headers) requires the proxy to see request contents, i.e. TLS termination for those hosts [unverified beyond the strings].
- Kits declare per-agent allow rules (claude kit: `api.anthropic.com`, `platform.claude.com`, `downloads.claude.ai`, `claude.com`, `code.claude.com`, `mcp-proxy.anthropic.com`, `bridge.claudeusercontent.com` "/remote-control and /teleport relay"). Codex kit comment: "Without this block codex has zero allowed domains under a restrictive (non-open) egress policy."
- `sbx policy log` "Show sandbox policy logs" — the way to find blocked hosts (owner found a `mise.run` → `mise.jdx.dev` redirect this way [local-observation]).
- gh/git: service secret `github` is proxy-injected; the codex kit sets `GIT_TERMINAL_PROMPT=0` because "a 401 from the credentials proxy (e.g. a bad or expired github secret) makes git open /dev/tty to ask for a username and hang" [binary-observed]. Docs (credentials page): "Store your GitHub token as a sandbox secret. The proxy injects it into outbound requests, so gh works inside the sandbox without any additional configuration." Bound domains: api.github.com, github.com, raw.githubusercontent.com, gist.github.com. `gcloud`/AWS: `claude-bedrock` kit exists ("requires the AWS CLI v2 to be installed on the host"), strings "bedrock: scheduling STS refresher", `GOOGLE_APPLICATION_CREDENTIALS` show cloud-credential brokering [binary-observed]; beyond `--ref` (1Password / AWS Secrets Manager) sourcing, gcloud/AWS mechanics are not documented.
- Documented architecture (https://docs.docker.com/ai/sandboxes/security/defaults/ , https://docs.docker.com/ai/sandboxes/architecture/): "All outbound TCP traffic from the sandbox routes through a proxy on your host." "All outbound TCP traffic, including HTTP, HTTPS, and SSH, is blocked unless an explicit rule allows the destination." Always blocked, not policy-changeable: "Direct network communication between sandboxes", "Direct external UDP and ICMP connections" (governance/network: `connect:udp` rules "have no effect"). The docs never say "MITM" or "CA injected" verbatim; TLS termination is implied by header rewriting and by the binary strings above. The exact "balanced" domain list is not published in the docs pages fetched (the local `sbx policy ls` count is the only enumeration).
- SSH: "SSH agent forwarding is enabled by default" (workflows/git). Issue #121 (open): with no secrets and the balanced policy, "I expect the agent to be able to pull public github projects only", yet the agent authenticated via the forwarded agent (https://github.com/docker/sbx-releases/issues/121). Issue #46 (open): "Network proxy drops outbound SSH (Port 22) during Key Exchange, ignoring explicitly 'Allowed' policies" (https://github.com/docker/sbx-releases/issues/46). Issue #8 (open): "HTTP proxy strips/modifies auth headers causing Claude Code Remote Control (CCR) bridge 401/403 failures" (https://github.com/docker/sbx-releases/issues/8).

### 1.6 Double sandbox stance

Docker's built-in kits disable or bypass the harness's own sandbox/permission layer inside the microVM: Claude `--dangerously-skip-permissions` + `permissions.defaultMode: bypassPermissions`; Codex `--dangerously-bypass-approvals-and-sandbox` + `sandbox_mode = "danger-full-access"` ("yolo mode"); Gemini `GEMINI_SANDBOX=false` + `tools.sandbox: false` + `--yolo`; Cursor `--yolo`; Devin `--permission-mode dangerous` [binary-observed sbx v0.43.0]. No kit enables bubblewrap/seatbelt/Landlock inside the VM. The proxy even strips a server-side flag that would block bypass mode: "proxy: removed disableBypassPermissionsMode from anthropic settings response" [binary-observed]. So Docker's de-facto stance is: the microVM is the boundary; the harness runs unguarded inside it. The owner's own kits override this back to Claude's `auto` mode via settings [local-observation 2026-08-15]: "VM boundary stops destruction but does not substitute judgment ... 'untrusted code so throw it in with bypassPermissions' is backwards."

Docker's stated position, verbatim (https://docs.docker.com/ai/sandboxes/faq/ , "Why do agents run without approval prompts?"): "The sandbox itself is the safety boundary. Because agents run inside an isolated microVM with network policies, credential isolation, and no access to your host system outside explicitly shared paths, the usual reasons for approval prompts (preventing destructive commands, network access, file modifications) are handled by the sandbox isolation layers instead." "If you prefer to re-enable approval prompts, change the permission mode inside the session... In Claude Code, use the /permissions command... To make approval prompts the default for every session, define a custom sandbox kit that overrides the agent's entrypoint to drop the permission-skipping flag." Agent pages confirm the launch lines: "Without extra args, the sandbox runs: claude --dangerously-skip-permissions" (https://docs.docker.com/ai/sandboxes/agents/claude-code/); "The sandbox executes: codex --dangerously-bypass-approvals-and-sandbox" (https://docs.docker.com/ai/sandboxes/agents/codex/). Maintainer position in issue #47 "opt out of yolo mode default" (closed, https://github.com/docker/sbx-releases/issues/47): "I think we'll keep YOLO the default experience for agents, but will explore way[s] to make the agent configuration more user configurable." ## 2. Anthropic — Claude Code

Sources: https://code.claude.com/docs/en/sandboxing , https://code.claude.com/docs/en/sandbox-environments , https://code.claude.com/docs/en/devcontainer , https://code.claude.com/docs/en/worktrees , https://code.claude.com/docs/en/claude-code-on-the-web , https://code.claude.com/docs/en/routines , https://github.com/anthropics/claude-code/tree/main/.devcontainer (devcontainer.json, Dockerfile, init-firewall.sh via `gh api`).

### 2.1 Repo into the box
- Dev container: bind mount. `devcontainer.json`: `"workspaceMount": "source=${localWorkspaceFolder},target=/workspace,type=bind,consistency=delegated"`. Trade-off stated: "Claude can still modify any file in the bind-mounted workspace, which appears directly on your host" (devcontainer doc).
- Cloud sessions: clone, not mount. "The cloud VM clones your current directory's GitHub remote at your current branch, not your local checkout, so push first if you have local commits." Without a usable remote, `claude --cloud` bundles: "Claude Code bundles your local repository and uploads it directly to the cloud session... includes your full repository history across all branches, plus uncommitted changes to tracked files", with credential-looking files (`.env`, `*.tfvars`, `id_rsa`, `*.pem`) excluded; 100 MB cap with fallbacks; `CCR_FORCE_BUNDLE=1` forces it (claude-code-on-the-web).
- Routines: "Each repository you add is cloned on every run. Claude starts from the repository's default branch unless your prompt specifies otherwise." (routines)
- `--worktree` / `-w`: creates a worktree "under `.claude/worktrees/<name>/` at your repository root, on a new branch named `worktree-<name>`"; `worktree.baseRef` = `"fresh"` (remote default branch) or `"head"`; `EnterWorktree`/`ExitWorktree` tools; entering a path outside `.claude/worktrees/` needs user approval; worktrees share `.git`, plugins and permission approvals; cleanup: unnamed interactive sessions auto-remove clean worktrees on exit, named prompt, `-p` runs leave them for a sweep keyed by `cleanupPeriodDays` (worktrees doc).
- Bash sandbox and worktrees: "Git worktrees: when the working directory is a linked git worktree, the sandbox also allows writes to the main repository's shared `.git` directory so commands such as `git commit` can update refs and the index. Writes to `hooks/` and `config` inside that directory remain denied." (sandboxing)

### 2.2 Config / creds into the box
- Dev container: `~/.claude` is a named volume, not the host dir: `"mounts": ["source=claude-code-config-${devcontainerId},target=/home/node/.claude,type=volume"]`. Warning that `~/.claude.json` is separate: "mounting a volume at `~/.claude` alone doesn't keep you signed in" — set `CLAUDE_CONFIG_DIR` to the mount so `~/.claude.json` lands in the volume. "Avoid mounting host secrets such as `~/.ssh` or cloud credential files into the container; prefer repository-scoped or short-lived tokens." Cloud-provider creds go in via `containerEnv`/Codespaces secrets/workload identity "rather than mounting credential files from the host." Blunt warning: `--dangerously-skip-permissions` in a dev container "do[es] not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`. Only use dev containers when developing with trusted repositories."
- Cloud sessions: credential proxy. "in Anthropic-hosted environments, git credentials and signing keys stay outside the sandbox, and a proxy authenticates on the session's behalf with scoped credentials"; API keys added to a cloud environment "stay outside the sandbox the same way, attached to matching requests after they leave the session." GitHub auth: GitHub App, or `/web-setup` which sends the local `gh` token to the Claude account.
- Sandboxed Bash tool (same machine): `sandbox.credentials` entries with `"mode": "deny"` or `"mode": "mask"`: "With `mask`, the sandboxed command sees a per-session sentinel value instead of the real one. Each `mask` entry can list `injectHosts`, the hosts the real value is allowed to reach. When a request leaves the sandbox for one of them, the sandbox proxy replaces the sentinel with the real value." "The proxy substitutes the credential inside request contents, so it has to see them. Set `network.tlsTerminate` so the proxy terminates TLS itself." Masking is honoured only from user/managed/`--settings` scopes, never from repo `.claude/settings.json`. AWS SigV4 re-signing supported via `credentials.awsPairs`. "`deny` removes the variable entirely, which also breaks tools that need it, such as `gh` or `npm`."

### 2.3 Work out
- Dev container: ordinary `git push` / `gh pr create` on the bind-mounted repo.
- Cloud: diff view against base branch, PR from claude.ai/code; auto-fix "receives GitHub events for the PR including new review comments and CI check failures" and pushes fixes.
- Routines: "Claude pushes its work to branches prefixed with `claude/`, which are always accepted."; other branches are rejected if protected / have someone else's PR / carry someone else's commits.

### 2.4 Resume
- Dev container: `~/.claude` volume survives restarts; keyed by `${devcontainerId}` so it is per-devcontainer-instance; discarded on rebuild unless the named-volume + `CLAUDE_CONFIG_DIR` pattern is used.
- Cloud: "Cloud sessions stop after a period of inactivity and the session's VM is reclaimed... Reopen the session from claude.ai/code to provision a fresh VM with your conversation history restored. Background work that was still running when the VM was reclaimed, such as subagents and shell commands, isn't restored." `--teleport` is one-way cloud→local: "Claude verifies you're in the correct repository, fetches and checks out the branch from the cloud session, and loads the full conversation history into your terminal." "you can pull cloud sessions into your terminal with `--teleport`, but you can't push an existing terminal session to the cloud".
- Routines: "Claude Code doesn't reuse sessions across events, so two PR updates produce two independent sessions".

### 2.5 Network
- Bash sandbox: default-deny domain allowlist via "a proxy server running outside the sandbox"; "Claude Code pre-allows no domains by default." Limitation, verbatim: "The built-in proxy enforces the allowlist based on the requested hostname and, by default, does not terminate or inspect TLS traffic. The experimental `network.tlsTerminate` setting, available in Claude Code v2.1.199 and later, makes the built-in proxy terminate TLS itself, which `mask` credential entries require." And: "Allowing broad domains such as `github.com` can create paths for data exfiltration. Because the proxy makes its allow decision from the client-supplied hostname without inspecting TLS, code running inside the sandbox can potentially use domain fronting or similar techniques to reach hosts outside the allowlist. If your threat model requires stronger guarantees, configure a custom proxy that terminates TLS and inspects traffic, and install its CA certificate inside the sandbox."
- Host tools: "Go-based CLIs fail TLS verification on macOS: tools such as `gh`, `gcloud`, and `terraform` may fail TLS verification under Seatbelt. List these tools in `excludedCommands`. If you are using `httpProxyPort` with a MITM proxy and custom CA, set `enableWeakerNetworkIsolation` to `true` instead." "`docker` commands fail: `docker` is incompatible with the sandbox. Add `docker *` to `excludedCommands`." "allowing access to `/var/run/docker.sock` effectively grants access to the host system through the Docker socket."
- Dev container: `init-firewall.sh` — default-deny iptables+ipset, allows DNS/SSH/loopback, resolves an explicit list (`registry.npmjs.org`, `api.anthropic.com`, `sentry.io`, `statsig.com`, VS Code hosts) plus GitHub IP ranges from `api.github.com/meta`, then self-tests (`example.com` must fail, `api.github.com/zen` must succeed). Requires `--cap-add=NET_ADMIN --cap-add=NET_RAW`; "The firewall script and these capabilities are not required for Claude Code itself".
- Cloud: "network access is limited by default and can be disabled... When running with network access disabled, Claude Code can still communicate with the Anthropic API, which may allow data to exit the VM." Default "Trusted" allowlist; MCP connector traffic goes via Anthropic's servers; denials return 403 with `x-deny-reason: host_not_allowed`.

### 2.6 Double sandbox stance — explicit, pro-layering with a named weaker mode
- "You can layer approaches: running the sandboxed Bash tool inside a container or VM gives you OS-level command restrictions on top of the outer environment boundary." and, under Custom container: "You can layer the built-in Bash sandbox inside the container for per-command restrictions. Unprivileged containers need the nested-sandbox setting described in Sandboxing troubleshooting." (sandbox-environments)
- "Bubblewrap fails to start inside a container: in an unprivileged container, bubblewrap can't mount a fresh `/proc` filesystem, so sandboxed commands fail with a `bwrap` error such as `Can't mount proc on /newroot/proc: Operation not permitted`. Set `enableWeakerNestedSandbox` to `true` so the inner sandbox bind-mounts the container's existing `/proc` instead. Only use this setting when the outer container already provides the isolation boundary you need, since it exposes process information to sandboxed commands that a fresh `/proc` mount would hide." (sandboxing)
- "Linux sandbox strength: the Linux implementation provides strong filesystem and network isolation but includes an `enableWeakerNestedSandbox` mode that enables it to work inside Docker environments without privileged namespaces, or on Linux hosts where unprivileged user namespaces are disabled by sysctl. This option considerably weakens security and should only be used when additional isolation is otherwise enforced." (sandboxing)
- Permission modes vs isolation: "Always run `--dangerously-skip-permissions` sessions inside a container, a VM, or the sandbox runtime, so that file tools, MCP servers, and hooks are also inside the boundary. On Linux and macOS, Claude Code refuses to start with this flag when running as root, so run the container, VM, or sandbox runtime as a non-root user." "Auto mode replaces the prompt with a classifier that reviews actions. The classifier is a per-action control, not an isolation boundary, so an isolation boundary still adds defense in depth for unattended runs". "The sandboxed Bash tool on its own constrains only shell commands, so it is not sufficient for fully unattended runs in either mode." (sandbox-environments)
- Whole-process wrapper: `@anthropic-ai/sandbox-runtime` "wraps an entire process in the same Seatbelt or bubblewrap isolation"; it requires write grants for `~/.claude`, `~/.claude.json`, `/tmp`; denies `.git/hooks`, `.git/config`, `.mcp.json`, `.claude/commands`, `.claude/agents`, shell startup files; on Linux "builds the deny list once at launch" and "does not cover anything the session creates later, such as `git init`, `git clone`". (sandbox-environments)

## 3. OpenAI — Codex and Symphony

Sources: https://learn.chatgpt.com/docs/environments/cloud-environment (redirect from https://developers.openai.com/codex/cloud/environments), https://learn.chatgpt.com/docs/cloud/internet-access , https://learn.chatgpt.com/docs/sandboxing , https://learn.chatgpt.com/docs/config-file/config-reference , https://learn.chatgpt.com/docs/environments/git-worktrees , https://github.com/openai/symphony (README, SPEC.md).

### 3.1 Repo into the box
- Cloud: "When you submit a prompt, Codex creates a container and checks out your repo at the selected branch or commit SHA." Cached container: "Codex checks out the branch specified for the chat". Cache lasts up to 12 h; "Codex automatically invalidates the cache if you change the setup script, maintenance script, environment variables, or secrets."
- Worktrees (app/CLI): "Codex creates worktrees in `$CODEX_HOME/worktrees`" by default; "The worktree isn't checked out as a branch. It's in a detached HEAD state."; `.worktreeinclude`: "Codex only copies ignored files that match .worktreeinclude; it doesn't copy other local files that Git doesn't track." (`AGENTS.override.md` auto-included); "By default, Codex keeps your most recent 15 Codex-managed worktrees." and before deletion "Codex saves a snapshot of the work on it".
- Symphony: VCS-agnostic by design — "Workspace preparation beyond directory creation (for example dependency bootstrap, checkout/sync, code generation) is implementation-defined and is typically handled via hooks." One persistent directory per issue at `<workspace.root>/<workspace_key>`; "Workspaces are intentionally preserved after successful runs". Invariants: agent cwd == workspace_path; workspace_path must resolve inside workspace_root; key sanitised to `[A-Za-z0-9._-]` with hash suffix.

### 3.2 Config / creds
- Cloud: setup scripts run with internet; env vars "persist throughout the chat"; secrets have "an additional layer of encryption" and are "only available to setup scripts" — stripped before the agent runs.
- Symphony: "Host-side tracker secret environment variables SHOULD NOT be inherited by the coding-agent child process... The runtime MUST execute advertised tool calls host-side ... and MUST NOT require the coding-agent child process to read raw tracker tokens from disk or environment." Literal credentials in `WORKFLOW.md` "SHOULD NOT be used when this isolation matters."

### 3.3 Work out
- Cloud: "When finished, the agent shows its answer and a diff of any files it changed." User opens PR from the result view.
- Worktrees: "Hand off to or from Local moves your chat and code so you can continue in the other checkout." (bidirectional between Local and Worktree).
- Symphony: "Ticket mutations (state transitions, comments, attachments, PR metadata) are typically handled by the coding agent through the selected adapter's provider-native tools... The service remains a scheduler/runner and tracker reader."

### 3.4 Resume
- Cloud: transcript persistence across VM reclaim not documented in pages fetched.
- Symphony: no durable DB — "Support tracker/filesystem-driven restart recovery without requiring a persistent database; exact in-memory scheduler state is not restored"; multi-turn continuation on the same live thread within one worker run up to `agent.max_turns`.

### 3.5 Network
- Cloud: internet off by default during agent execution; presets "None", "Common dependencies" (~70 domains), "All (unrestricted)"; plus "restrict network requests to GET, HEAD, and OPTIONS". Threat model named: "prompt injection from untrusted content, code exfiltration, malware downloads, and license violations". TLS/MITM internals: not documented.
- Local workspace-write: "commands can reach only required hostnames from a managed allowlist" when public internet is disabled. Config keys: `sandbox_mode`, `sandbox_workspace_write.network_access`, `sandbox_workspace_write.writable_roots`, `exclude_slash_tmp`, `exclude_tmpdir_env_var`, `approval_policy`.
- Symphony: pass-through — `codex.thread_sandbox: workspace-write` default, `turn_sandbox_policy` with `networkAccess: true` needed "otherwise DNS/network access may be denied by the Codex turn sandbox".

### 3.6 Double sandbox stance — silent
- Enforcement: "Codex uses the built-in Seatbelt framework" (macOS); "Codex uses the first `bwrap` executable it finds on `PATH`" (Linux/WSL2), "If no `bwrap` executable is available, Codex falls back to a bundled helper", "Codex surfaces a startup warning when `bwrap` is missing"; native Windows sandbox in PowerShell. (learn.chatgpt.com/docs/sandboxing). Note: the current doc names bubblewrap, not Landlock+seccomp, for Linux; the earlier Landlock description was not found in the pages fetched.
- "The page contains no mentions of Docker, CI/CD integration, or running Codex within containers." No config key for nested containers. `gh` issue search on openai/codex for "docker landlock"/"sandbox docker" found no relevant thread. Docker's codex kit resolves this by running `--dangerously-bypass-approvals-and-sandbox` (section 1.6).
- Symphony Non-Goals: "Mandating strong sandbox controls beyond what the coding agent and host OS provide" and "a single default approval, sandbox, or operator-confirmation posture".

### 4.5 Coder — envbox, agentapi, Coder Agents, Agent Firewall

## 8. Which patterns dominate, which are rare

Dominant
1. Local boxes bind-mount the working tree; hosted boxes clone. Docker Sandboxes (default), Anthropic dev container, Dev Containers spec default, agent-deck, ccmanager all bind-mount. Every hosted product (Claude cloud, Codex cloud, Cursor, Jules, Copilot, Routines) clones at a branch/SHA. Bind-mount trade-off is stated identically by Docker and Anthropic: edits appear directly on the host.
2. Credentials via a proxy or by reference, not by copying files in. Docker (service secrets + OAuth sentinels), Anthropic cloud (scoped-credential proxy), Anthropic Bash sandbox (`mask` + `injectHosts`), Codex cloud (secrets only during setup), container-use (`op://` refs), Coder (control plane calls providers), OpenShell for pi. The vendors that do copy auth in (agent-deck, pi plain Docker, Sculptor token) each document a caveat (Keychain fork, exposed auth files, unvalidated token).
3. Partial, per-subdirectory persistence of `~/.claude` rather than mounting the host's `~/.claude`. Docker mounts five subdirectories as volumes and regenerates `settings.json`/`.credentials.json`, and its FAQ states user-level config "remain[s] on the host"; Anthropic uses a per-devcontainer named volume plus `CLAUDE_CONFIG_DIR`. Nobody documents mounting the host's real `~/.claude` read-write; the one attempt on record (Docker #113, `~/.claude:ro`) fails on the host-path/UID mismatch.
4. Results come out as git objects: branch on a remote (hosted products, Routines' `claude/` prefix), a git remote exposed from the box (Docker `sandbox-<name>` via git daemon), or branch-per-environment (container-use). Diff-copying is a UI affordance (Codex, Claude cloud diff view, `amp sync`), not the transport.
5. Resume = re-attach a named box whose state volume persists (Docker, Amp orbs, E2B pause, dev container volume), or server-side transcript rehydrated into a fresh VM (Claude cloud, Coder DB). Routines/Symphony deliberately do not resume.
6. Network = default-deny (or curated) domain allowlist enforced by a proxy outside the agent's reach. Docker balanced, Anthropic Bash sandbox, dev container iptables, Codex "Common dependencies", Modal/Daytona allowlists, Coder Agent Firewall.
7. Inside a VM/container, vendors run the harness in bypass/yolo mode. Docker's kits for Claude, Codex, Gemini, Cursor, Devin, OpenCode and its FAQ ("The sandbox itself is the safety boundary"); ccmanager's stated purpose; Anthropic's own advice pairs `--dangerously-skip-permissions` with a container/VM. The two documented dissents are Anthropic ("The classifier is a per-action control, not an isolation boundary, so an isolation boundary still adds defense in depth" — i.e. keep both) and the user objection in Docker #47 (history rewrite inside the box is still an attack on the host).
8. Worktree managers converge on `.worktreeinclude` and a setup script for copying ignored files.

Rare
1. Explicit double-sandbox guidance: only Anthropic (pro-layering with `enableWeakerNestedSandbox`) and Coder (its own nsjail/Landlock jail). Codex, Docker, and every platform are silent; Docker's kits actively turn the inner sandbox off.
2. TLS-terminating proxies: Docker (L7 MITM, binary-observed), Anthropic `tlsTerminate` (experimental, only for masking), Modal sidecar (experimental), Daytona `outboundProxyUrl`. Default everywhere is hostname/SNI-only.
3. HTTP-method restriction: Codex cloud (GET/HEAD/OPTIONS) and Coder Agent Firewall only.
4. Git worktree as the thing that goes into a box: none of the box tools document a worktree workspace; Claude Code's sandbox and `--worktree` are the only combination with documented semantics (shared `.git` writes allowed, `hooks/`/`config` denied). Codex worktrees are detached-HEAD.
5. Bidirectional session transfer: Codex Handoff (Local↔Worktree). Claude `--teleport` is one-way.
6. Credential copying into the box with a documented Keychain hazard: agent-deck and Sculptor only.
7. Whole-process wrappers without containers: Anthropic sandbox-runtime, pi Gondolin, Coder landjail.

## 9. Design constraints for a solo developer's multi-CLI "box" command (with precedent)

1. Make repo ingress an explicit two-way choice — bind mount for "edit in place", clone for "cannot destroy the host tree" — and say which one is active. Precedent: Docker `--clone` flag text and Anthropic's dev container warning ("appears directly on your host"); Dev Containers' bind-vs-volume rationale.
2. In clone mode, treat the read-only source mount as a disclosure surface, not a secret boundary; only network policy stops exfiltration. Precedent: Docker `/run/sandbox/source` [local-observation]; Anthropic: "Any approach that allows network egress can still leak data the agent can read".
3. Never mount the host's whole `~/.claude` (or `~/.codex`, `~/.pi/agent`); persist only session subdirectories, and regenerate `settings.json`/credential files per box. Precedent: Docker claude kit volumes and comment; Anthropic named volume + `CLAUDE_CONFIG_DIR`; pi's "exposes authentication files" caveat; the owner's note that the whole dotfiles repo would expose ~1.7 GB of transcripts [local-observation].
4. Put credentials behind a proxy or a reference scheme; if a token must be copied, use a short-lived/scoped one and never the macOS Keychain OAuth entry. Precedent: Docker service secrets; Anthropic `mask`/`injectHosts`; container-use `op://`; agent-deck Keychain exception; Sculptor `claude setup-token`; Anthropic "prefer repository-scoped or short-lived tokens".
5. Export results as git refs, never as loose diffs: `sandbox-<name>` remote (Docker), `claude/`-prefixed branches (Routines), branch-per-environment (container-use). Re-resolve the git-daemon port on every start; do not cache it — Docker's CLI rewrites the remote URL on restart and removes it on `sbx rm`, and the daemon is fetch-only (#367). Expect no push-into-box path; hand work in by re-creating the box or via `sbx cp`.
6. Resume by name: a box's identity = its name = its state volumes; `-- --continue` must map to the box's own `~/.claude/sessions` + `projects`. Precedent: Docker kit ("Load-bearing for `claude -c`"), Amp orbs, E2B pause. No precedent found for mounting the host's transcript directory into a box for resume; ccmanager copies `~/.claude/projects/<path>` between worktrees on the host, which is the nearest analogue.
7. One name → one workspace path inside the box that equals the host path, so `~/.claude/projects/<workspace-as-dashes>` keys line up across host and box. Precedent: Docker ("equals the host path on macOS/Linux bind mounts"); cursor kit's workspace-slug trust file. No precedent found for keeping host and box transcripts in sync.
8. Network: start from a curated allowlist, add per-agent allow rules in the agent's own kit, allow per-box deny-only narrowing, and keep a policy log to find blocked hosts. Precedent: Docker `policy init balanced` + kit allow + `--deny-network` ("can only narrow, never widen"), `sbx policy log`; Codex kit comment "zero allowed domains under a restrictive (non-open) egress policy".
9. Expect Go CLIs (`gh`, `gcloud`, `terraform`) and `docker` to need either an exclusion from the inner sandbox or a real CA-installed MITM proxy; hostname-only allowlists are defeatable by domain fronting. Precedent: Anthropic troubleshooting and security-limitations sections; Docker's L7 MITM proxy [binary].
10. Decide the double-sandbox posture per CLI and write it down. Options with precedent: (a) VM is the boundary, inner sandbox off (Docker kits, ccmanager); (b) inner Bash sandbox layered inside with `enableWeakerNestedSandbox` when the container is unprivileged (Anthropic); (c) a platform-owned process jail (Coder Agent Firewall). No precedent found for running Codex's `bwrap` sandbox inside a container; Codex docs are silent and Docker bypasses it. For Gemini, Docker sets `GEMINI_SANDBOX=false`. Do not run as root if `--dangerously-skip-permissions` is used (Anthropic refuses).
11. Keep judgment separate from isolation: a permission mode (Anthropic `auto` classifier) is "a per-action control, not an isolation boundary"; the box is not a reason to drop it. Precedent: Anthropic sandbox-environments; the owner's kits run `auto` inside the VM [local-observation]. No vendor kit ships this combination by default.
12. Multi-CLI parity: expect each CLI's in-box config to be regenerated by the box tool (Docker rewrites `~/.claude/settings.json`, `~/.codex/config.toml`, `~/.gemini/settings.json` on every create), so user-layer settings must be applied after/over that rewrite, not by replacing the file. Precedent: Docker kit comments ("engine-managed and rewritten unconditionally"; codex `config.toml` "is shared territory ... Append ... rather than overwriting").
13. Skills/rules: mount a shared store read-only at the agent's skills dir, or opt out; a read-write mount is a cross-box write channel and blocks symlink managers. Precedent: Docker `--skills readonly|readwrite|off` and the owner's "Device or resource busy" finding [local-observation]. No precedent found for mounting hooks/rules directories (Docker only handles skills; Anthropic sandbox-runtime denies writes to `.claude/commands`, `.claude/agents`, `.mcp.json`).
14. Worktrees: if the box workspace is a linked worktree, the shared `.git` must also be reachable (read-write for refs/index, read-only for `hooks/` and `config`), and the parent checkout's untracked files must not be. Precedent for the requirement: Anthropic sandboxing doc. Precedent for the failure modes: Docker docs ("mounts only the worktree directory ... has no Git access. The agent can read and write files, but can't commit, branch, or check status") and issues #154 (parent-dir traversal read `.env.local`), #101 (worktrees under `.sbx/` deleted on `sbx rm`), #432 (CLAUDE.md placement). No box tool documents a working worktree-as-workspace mode; Docker's `--clone` is the vendor-offered alternative.

14a. Do not rely on symlinks into host paths for config delivery; the vendor says they cannot be followed, and the in-box user/home differs from the host's. Precedent: Docker FAQ ("Don't use symlinks to host paths because a sandboxed agent can't follow them outside the sandbox") and #113 (`/home/agent` vs host `$HOME`). Deliver config by kit `files/home/` or by mounting specific directories at the in-box home path, not at the host's absolute path.

14b. SSH agent forwarding is on by default in Docker Sandboxes and is a credential channel the network policy does not govern (#121); a "no credentials" posture must disable it explicitly. No other box tool documents forwarding an SSH agent by default (VS Code dev containers forward it, but as an opt-in extension behaviour).
15. Non-interactive/scripted use needs a detached create + exec path and a non-blocking git credential prompt. Precedent: Docker `--detached` and `GIT_TERMINAL_PROMPT=0` in the codex kit; sandbox-agent's "SSH with piped commands breaks tool confirmations".

Explicit "no precedent found" list: host-transcript sync into/out of a box; a working worktree-as-workspace mode in any box tool; a vendor kit that keeps the harness's permission classifier on inside a VM (Docker's FAQ points to a custom kit; the only public example, `kits-cookbook/claude-safe`, restores prompts rather than `auto`); Codex's inner sandbox running inside a container; a push-into-box path for Docker's git daemon; a published enumeration of Docker's "balanced" allowlist; DSH sandbox guidance.
