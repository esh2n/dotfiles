### Usage evidence (jig, 30-day window, run read-only)

`bun jig.ts report skills --days 30` executed successfully: 3,411 session
files touched, 7,948 turns read (2026-08-15→2026-09-22), across two harnesses
(`claude`: 7,757 turns, `pi`: 191 turns — Codex/DSH/omp transcripts were not
in the scanned roots). Headline numbers:

- 96% of turns involved no skill at all.
- Of turns where the router injected a skill description, only 12 were
  followed, 198 were ignored (injected-but-not-opened) — a **6% follow rate**
  on router injections in this window.
- 69 turns opened a skill the router never scouted ("unscouted") — jig's own
  caveat: "a request the router declined leaves no trace, so 'opened one
  unscouted' is an upper bound on misses."
- Of the 88 skills inventoried in Part A, **54 appear at all** in 30 days of
  transcripts (opened ≥1 time); **34 have zero recorded opens** — almost
  entirely the language packs (java, kotlin, php, perl, django, cpp, rust,
  gcp, k8s, clean-arch, ddd, event-driven, observability, sql-tuning,
  cloudflare, human-interface-guidelines, ui-ux-pro-max, frontend-craft).
  This matches the user's actual working languages (Go/TypeScript/Python
  dominate the opened list) and is evidence the pack system, not individual
  skill authoring, is the right lever for reducing idle context — pruning
  single skills inside a dormant pack (e.g. deleting `kotlin-testing` alone)
  would not move the needle; disabling the whole `kotlin` pack would.

### Lens 1 — Vendors

**Claude Code** (`code.claude.com/docs/en/skills.md`, direct fetch, 2026-09-22):
supports a superset of fields beyond what this profile uses —
`when_to_use`, `arguments`, `allowed-tools`, `disallowed-tools`, `model`,
`effort`, `context: fork`, `agent`, `background`, `paths`, `shell`, `hooks`,
in addition to `disable-model-invocation` and `user-invocable` (which this
profile never sets). Progressive disclosure is explicit and load-bearing:
> "the combined `description` and `when_to_use` text is truncated at 1,536
> characters in the skill listing to reduce context usage" and "Keep
> `SKILL.md` under 500 lines. Move detailed reference material to separate
> files." [summarized fetch]
Claude Code also ships a **`/skill-doctor`** command whose stated purpose is
exactly this task, ongoing: "Run `/skill-doctor` to see what each of your
skills costs and how often it gets used, so you can decide which ones to turn
off... start with the ones that have the highest context cost." [summarized
fetch] — i.e. Anthropic has already built the tool this research task is
approximating by hand with `jig`; `/skill-doctor` was not run in this survey
(out of scope; `jig report skills` was used instead per the task's own
instruction) but is worth running as a cross-check.

**Anthropic's tool-use guidance**

   because of that overlap.
6. A **skill-security-scanning habit**, not a specific SKILL.md: the
   AI Skill Shield finding (lens 4) that Anthropic's own official plugin
   repo scored 3 critical / 11 high is itself the strongest argument in

## Verdict

The evidence supports three concrete moves, in order of strength:

1. **Add `using-git-worktrees` and `verification-before-completion` from
   `obra/superpowers`** (MIT, 289,976★, pushed one day before this survey).
   Both fill a gap this survey confirmed empirically in Part A (no installed
   skill in 88 owns worktree isolation or pre-completion evidence-gating),
   and one of the two maps directly onto a failure mode already in this
   user's own memory record. This is the single most decision-relevant
   finding — everything else in this report is context, this is the action.
2. **Stop authoring per-skill fixes inside dormant packs.** `jig`'s 30-day
   data shows 34 of 88 installed skills were opened zero times, and they
   cluster entirely by *pack* (java, kotlin, php, perl, django, cpp, rust,
   gcp, k8s, clean-arch, ddd, event-driven, observability, sql-tuning,
   cloudflare, design). The lever that matches this evidence is
   `yoki-switch pack enable|disable`, not editing individual SKILL.md files.
3. **Treat any newly-vendored skill as untrusted text before installing it**,
   including the two recommended above: a scanner found critical-severity
   dangerous patterns inside Anthropic's own official plugin repo. Read the
   fetched SKILL.md in full before adding it to `personal/skills/` or a pack,
   the same discipline `natural-japanese/UPSTREAM.md` already models for this
   tree (pinned commit, documented rsync path, explicit exclusions).

What the evidence does **not** support: a numeric target for "how many
skills is too many," or a measured accuracy delta from skill count or
description length. Every vendor source that touches this question stops at
a context-budget mechanism (character/percentage caps) or a qualitative
warning, never a task-outcome number. Any claim of the form "N skills is the
right number" would be this survey's own invention, not something found.
