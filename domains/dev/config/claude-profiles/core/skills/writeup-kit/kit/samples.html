画像アップロードの再試行方針

画像アップロードに失敗したときの再試行方法を、実装担当者向けに1つに決める。結論は指数バックオフと上限3回で、キューへの移譲は次のフェーズに送る。

画像アップロードに失敗する原因の大半は、一時的なネットワーク断とサーバー側の過負荷である。

方針は指数バックオフでの自動再試行を最大3回まで行い、それでも失敗したら手動再試行に切り替える。

サーバー側キューへの移譲は運用負荷が高いため今回は見送り、次のフェーズの検討事項とする。

目的と読者

このドキュメントは、画像アップロード機能の実装担当者と、それをレビューするテックリード向けに、失敗時の再試行方針を1つに決めることを目的とする。読者が持ち帰るべき結論は1つだけで、既定の再試行方式を指数バックオフにする、という点である。

メモ: wu-accent — 使うとき: 読者が1つだけ持ち帰る点／使わないとき: 2箇所目。

用語

指数バックオフ
再試行のたびに待機時間を倍にしていく方式。
冪等キー
同じ処理が複数回届いても、結果が1回分になるようにするための識別子。
デッドレターキュー
上限回数まで失敗した処理を、後で調べられるように退避させておく場所。

現状とギャップ

現在のクライアントは失敗時に再試行を行わず、ユーザーが手動でもう一度アップロードボタンを押す必要がある。

モバイル回線での失敗率は、Wi-Fi接続時の約4倍という計測結果がある。

この計測は、アプリのクラッシュレポート基盤から取得した直近30日分の集計に基づく。

再試行の上限を決めずに実装すると、障害発生時にサーバー全体の負荷が跳ね上がる。

この失敗パターンは、過去の障害対応でも繰り返し確認されている。

したがって、再試行の上限は3回で固定し、利用者側の設定では変更できないようにする。

決定点

案実装コスト失敗時の体験運用負荷
固定間隔で再試行低障害時に一斉再試行が起きやすい低
指数バックオフ中負荷を分散できる中
サーバー側キューに移譲高体験は最も安定する高

決めたこと

決定: 再試行は指数バックオフとし、上限は3回とする。

重視した得失: 実装コストを抑えつつ障害時の一斉再試行を避けることを優先し、体験の完全な安定は次フェーズに送った。

根拠: 直近の障害はいずれも再試行の集中が原因で、上限と待機時間の調整だけで再発を防げる見込みが立った。

進め方

  1. 再試行ロジックを共通アップロードクライアントに実装する。
  2. 冪等キーをアップロードAPIのリクエストヘッダーに追加する。
  3. 上限に達した処理をデッドレターキューへ退避する処理を実装する。
  4. 障害訓練で上限3回の挙動と負荷への影響を確認する。

Clients SHOULD NOT retry a request that has already succeeded from the server's perspective; use an idempotency key to make retries safe.

クライアントは、サーバー側からは成功済みとみなされているリクエストを再試行すべきではない。冪等キーを使い、再試行を安全にすること。
