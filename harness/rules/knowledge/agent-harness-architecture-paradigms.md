# ルールベースのツールコール・ガードは十分なセキュリティ境界か、専用の判断モデルはどこまで有効か

確認日: 2026-09-22

## 答え

ルールベースのガード（Bash/Write/Edit/MCPの呼び出しを正規表現/globのポリシーでallow/ask/deny判定し、fail-closedで運用する方式）は、あらゆる角度からの調査で「OSレベルのサンドボックスの上に乗る、必要な防御の一層」として支持されるが、「それ自体がセキュリティ境界になる」ことは一度も支持されなかった。ポリシー表現・確認・監査の層としては本物の価値があるが、動機のある攻撃者に対する境界にはならない。専用の「判断モデル」（安価な別モデルにルーティング・スキル選択・圧縮の判断だけをやらせる仕組み）は、モデル階層のルーティングに限っては明確に裏付けがある（コストギャップが大きく、判断に必要な情報が軽い）。しかしスキル選択と圧縮については裏付けがなく、条件（大きなコストギャップ、軽い情報だけでの判別可能性）を満たしていない可能性が高く、Anthropic自身のClaude Codeはこの二つをメインモデル自身にやらせている。

## 根拠

- AgentDojo（arXiv:2406.13352）: ツールフィルタリング防御は攻撃成功率を7.5% まで下げるが0% にはならず、「必要なツールが攻撃の実行にも十分な場合」に該当するテストケースの17% で構造的に失敗する。
- AnthropicのClaude Codeドキュメント（`code.claude.com/docs/en/sandbox-environments`, `.../permissions`）: 「分類器はパー・アクションの制御であって隔離境界ではない」「`Bash(command:rm *)`のようなルールは複合コマンドで回避可能なためClaude Code自身が無視し起動時に警告する」と明記。
- OpenAIのCodexドキュメント: サンドボックスと承認ポリシーは独立した二層であり、承認を無効化してもサンドボックスの強度は変わらないと明記。
- GoogleのSAIFホワイトペーパー: 決定的なポリシーエンジン（ルール層）を「テスト可能・監査可能」だが「未想定の文脈では正当な行動を塞いだり有害な行動を通したりしうる」と評価し、推論ベースの層と並ぶ「二層とも必須、どちらか単独では不十分」という立場を取る。
- 実際に開示された回避事例: Claude Codeのコマンド許可リストが`ping`/`nslookup`/`dig`を安全と分類していたためDNS経由のデータ持ち出しに使われた（CVE-2025-55284）。AnthropicのFilesystem MCPサーバーはパスの`startsWith`比較のみで許可判定していたため、兄弟ディレクトリに漏れた。
- RouteLLM（arXiv:2406.18665）・Hybrid LLM（arXiv:2404.14618）・FrugalGPT（arXiv:2305.05176）は、モデル階層ルーティングに限って専用の安価な判断層がコストを大きく下げつつ品質を維持できることを実測で示している。
- Anthropicのドキュメント: Claude Codeはスキル選択も圧縮も、専用の判断モデルではなくメインモデル自身が行うと明記している（"we implement this by passing the message history to the model to summarize and compress the most critical details"、スキルはsystem prompt中のdescriptionをメインモデルが読んで選ぶ）。

## 注意点

- 「fail-closedでharness非依存の一つのポリシーを複数ハーネスに適用する」という設計自体は、調査した範囲のどのベンダーにも前例がない——正しい選択ではあり得るが、業界標準の実装ではなく独自の設計だと認識しておくべき。
- スキル選択・圧縮について「専用判断モデルがmainモデル自身に勝る」ことを示す一次資料も、逆に「劣る」ことを示す一次資料も見つからなかった——沈黙は肯定の証拠ではない。
- Googleの枠組み（ルール層を「補助」ではなく「対等な必須層」とする）はAnthropic/OpenAIの枠組み（ルール層はサンドボックスに従属するUX層）と強調点が異なる。どちらも「ルール単独では不十分」という結論では一致している。
- 「圧縮に外部ジャッジを使うと悪い」という直接の失敗事例（null result）は見つからなかった——推論であって実測ではない。
