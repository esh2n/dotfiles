# Decision records that humans find and AI coding agents obey (2025-2026)

Research record, 2026-09-22. Question: how do teams and notable practitioners record decisions ("we decided X because Y, rejected Z", rules adopted after a correction) so that (a) humans find them later and (b) coding agents (Claude Code, Codex, pi, DSH, Cursor, ...) read and obey them in later sessions? What dominates, what is rare, and what evidence says it works or fails.

Method: four parallel research lanes (classic ADR practice; vendor docs; practitioner posts; obedience evidence and linters) plus direct reads of the DeepSeek Harness repo via `gh api`, GitHub code-search counts via the legacy `search/code` API, and direct checks of log4brains / adr-tools / Backstage. WebSearch budget ran out mid-task, so late items were reached by direct fetch of known URLs, `gh`, HN Algolia, and Wayback. Every claim carries a URL. Verbatim quotes are in quotation marks. `[unverified]` marks anything inferred or not opened first-hand. `[via lane]` marks a subagent-opened source I did not re-open.

## 1. Classic ADR practice and its 2026 state

### 1.1 Nygard's original (2011) — https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions

- Sections: Title ("short noun phrases"), Context ("describes the forces at play, including technological, political, social, and project local... value-neutral"), Decision ("stated in full sentences, with active voice. 'We will …'"), Status ("A decision may be 'proposed' if the project stakeholders haven't agreed with it yet, or 'accepted' once it is agreed. If a later ADR changes or reverses a decision, it may be marked as 'deprecated' or 'superseded' with a reference to its replacement."), Consequences ("All consequences should be listed here, not just the 'positive' ones.").
- Location and numbering: "keep ADRs in the project repository under doc/arch/adr-NNN.md"; "ADRs will be numbered sequentially and monotonically. Numbers will not be reused."
- Never delete: "If a decision is reversed, we will keep the old one around, but mark it as superseded." Length: "one or two pages long. We will write each ADR as if it is a conversation with a future developer."

### 1.2 MADR 4.0 — https://adr.github.io/madr/ (adr/madr: 2,500 stars, latest release 4.0.0 on 2024-09-17, last push 2026-08-28)

- adr.github.io definitions: an ADR "captures a single AD and its rationale"; "The collection of ADRs created and maintained in a project constitute its decision log." https://adr.github.io/
- Directory `docs/decisions`, filename `NNNN-title-with-dashes.md` ("NNNN indicates the next number in sequence"). Optional front matter: title, status, date, decision-makers, consulted, informed. Status: "proposed | rejected | accepted | deprecated | … | superseded by ADR-0123".
- Sections: Context and Problem Statement; Decision Drivers; Considered Options; Decision Outcome ("Chosen option: "{title of option 1}", because {justification…}"); Consequences ("Good, because …" / "Bad, because …"); Confirmation ("Describe how the implementation of/compliance with the ADR can/will be confirmed."); Pros and Cons of the Options; More Information. Template: https://github.com/adr/madr/blob/main/template/adr-template.md
- Tooling list https://adr.github.io/adr-tooling/ (16 tools) has no mention of AI, LLMs, agents or MCP.

### 1.3 Tools — mostly dormant

- adr-tools https://github.com/npryce/adr-tools : "The default directory is `doc/adr`"; `adr new -s 9` "will create a new ADR file that is flagged as superceding ADR 9, and changes the status of ADR 9". 5,699 stars; latest release 3.0.0 on 2018-07-25; last push 2024-04-25 (`gh api`).
- log4brains https://github.com/thomvaill/log4brains : "Docs-as-code: ADRs are written in markdown, stored in your git repository, close to your code", default `./docs/adr`, static-site output; 1,593 stars; v1.1.0 on 2024-12-17 ("After a very long pause, I am very happy to release log4brains v1.1.0"); last push 2024-12-17.
- joelparkerhenderson/architecture-decision-record https://github.com/joelparkerhenderson/architecture-decision-record (17k stars): 12 templates; "Some teams much prefer the name 'decisions' over the abbreviation 'ADRs'. When some teams use the directory name 'decisions', then it's as if a light bulb turns on". README now: "This repository ships two Claude Code skills under skills/, so an AI coding agent can write and maintain ADRs the way this project recommends." — the most-starred ADR resource with explicit agent support.

### 1.4 Vendor / company guidance

- AWS Prescriptive Guidance https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html : "When the team accepts an ADR, it becomes immutable. If new insights require a different decision, the team proposes a new ADR." "Every team member can create an ADR, but the team should establish a definition of ownership for an ADR." Enforcement is by code review: "a code reviewer might find changes that violate one or more ADRs. In this case, the reviewer asks the author of the code change to update the code, and shares a link to the ADR." Rejections keep "a reason for the rejection to prevent future discussions on the same topic."
- Google Cloud https://docs.cloud.google.com/architecture/architecture-decision-records (reviewed 2024-08-16): "Store your ADRs close to your application code, ideally in the same version control system." Wiki/Docs only "for users not part of the ADR's team."
- Spotify (2020-04-14) https://engineering.atspotify.com/2020/04/when-should-i-write-an-architecture-decision-record : triggers are backfilling a "blessed" decision, closing an RFC ("Write an ADR!"), and small changes ("ADRs can be lightweight"); no storage location prescribed.
- GitHub blog (2020-08-13) https://github.blog/engineering/why-write-adrs/ : "ADRs will help you 6-12 months from now recall what your mindset was when you decided upon that architecture."; "decision socialization".
- Fowler bliki (2026-03-24) https://martinfowler.com/bliki/ArchitectureDecisionRecord.html : "The common advice is to keep decision records in the source repository of the code base to which they apply. A common choice for their location is `doc/adr`." "Once an ADR is accepted, it should never be reopened or changed - instead it should be superseded." No AI/agent mention.
- ThoughtWorks Radar "Lightweight Architecture Decision Records" https://www.thoughtworks.com/radar/techniques/lightweight-architecture-decision-records : Trial Nov 2016, Adopt Nov 2017 and May 2018 — "We recommend storing these details in source control, instead of a wiki or website, as then they can provide a record that remains in sync with the code itself."

- Ask HN 2023 https://news.ycombinator.com/item?id=36209777 : "As tribal knowledge departs, ADRs become lonely artifacts of what was and could have been"; "folks will pretend not to read your links and just do their own thing anyway."

- dev.to 2026-01-25 https://dev.to/tosin2013/how-to-automate-adr-reviews-and-keep-your-architectural-decisions-in-sync-with-your-codebase-kdn : "ADRs start as living documents and end up as digital dust collectors."
- arXiv 2609.07375 (2026-09-07) https://arxiv.org/abs/2609.07375 — dataset from "~550 open-source repositories"; "alternatives, decisions drivers, and some quality concerns remain under-documented."
- HN engagement on ADR posts is consistently 2-6 points, 0-5 comments (2019-2026) — a settled, low-controversy practice [inference].

### 1.6 ADRs in the agent era (2025-2026)

- Blog: dev.to 2026-09-19 "ADRs for AI coding agents" https://dev.to/naman_here/adrs-for-ai-coding-agents-how-to-make-every-agent-read-architecture-decisions-3he4 — "A record in the repository is available to an agent, but availability is not the same as context."; "Status is part of the data, not decoration." Mechanism: retrieval instructions in AGENTS.md/CLAUDE.md, a `.cursor/rules/architecture-decisions.mdc`, a `docs/adr/README.md` index, status frontmatter.
- Blog: arnaudp.dev 2026-03-15 https://www.arnaudp.dev/solving-ai-sprawl-using-git-worktrees-and-adrs-to-govern-parallel-agents-2/ — "They don't know that the team decided against UUIDs as primary keys in ADR-0001. They see files, not systems."
- Tools (stars as of today, all small): archgate/cli 68 https://github.com/archgate/cli ("Enforce Architecture Decision Records as executable rules — for both humans and AI agents"; `.archgate/adrs/ARCH-001-x.md` + companion `.rules.ts`; "Write an ADR once. Enforce it everywhere."; plugins for Claude Code/Cursor/VS Code/Copilot CLI/opencode); archcore-ai/cli 66; me2resh/agent-decision-record 48 ("Agent Decision Records (AgDR)", `docs/agdr/AgDR-0001-*.md` with agent/model/trigger frontmatter); rvdbreemen/adr-kit 9 https://github.com/rvdbreemen/adr-kit ("Architecture decisions your AI coding agents actually follow"; PreToolUse/PostToolUse hook injection; Claude Code/Codex/Copilot CLI/OpenCode); Decision Guardian https://github.com/DecispherHQ/decision-guardian (surfaces ADRs on PRs; "Resolution is human — override or update the ADR."); Mneme https://github.com/TheoV823/mneme ("ADR enforcement for AI coding agents"); EvolveHQ/docflow 13 (ADR workflow for Claude Code and pi; "AGENTS.md serves as the entry point", CLAUDE.md re-exports it); mbeacom/adrkit 17; memvid/adrflow 10. GADR arXiv 2608.17694 https://arxiv.org/abs/2608.17694 (LLM generation of ADRs from transcripts).
- No first-party vendor (Anthropic, OpenAI, GitHub, Cursor) or AWS/Google/Fowler prescribes reading `docs/adr` or `docs/decisions` as an agent convention. Agent-oriented ADR adoption is real but consists of one mainstream template repo adding Claude Code skills, roughly 15 tools under 70 stars each, and a few 2026 posts — all framing ADRs as an enforcement/retrieval problem rather than a documentation one.

## 2. Agent-oriented decision and rule records

### 2.1 What every harness actually loads (vendor docs, primary sources)

**Claude Code** — https://code.claude.com/docs/en/memory

- Two memory systems, both loaded every session, both advisory: "Both are loaded at the start of every conversation. Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead. The more specific and concise your instructions, the more consistently Claude follows them."
- Table: CLAUDE.md = "Instructions and rules" written by you; auto memory = "Learnings and patterns" written by Claude, "Per repository, shared across worktrees", loaded "Every session (first 200 lines or 25KB)". Auto memory holds "Your preferences, corrections you give Claude, project context Claude can't derive from the code" and is "machine-local".
- Injection: "CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself. Claude reads it and tries to follow it, but there's no guarantee of strict compliance, especially for vague or conflicting instructions."
- Decisions are explicitly in scope for CLAUDE.md: project CLAUDE.md should hold "build and test commands, coding standards, architectural decisions, naming conventions, and common workflows". When to add: "Claude makes the same mistake a second time / A code review catches something Claude should have known about this codebase / You type the same correction or clarification into chat that you typed last session".
- Size: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Hard skip at 4 MiB. "Consistency: if two rules contradict each other, Claude may pick one arbitrarily." `/doctor` "keeps pitfalls, rationale, and conventions that differ from tool defaults" and cuts derivable content.
- `@path` imports: "Imported files are expanded and loaded into context at launch alongside the CLAUDE.md that references them" (max depth four hops). Imports do not save context: "imported files still load and enter the context window at launch".
- `.claude/rules/*.md`: "Rules without paths frontmatter are loaded at launch with the same priority as .claude/CLAUDE.md." With `paths:` frontmatter, "Path-scoped rules trigger when Claude reads files matching the pattern". User-level `~/.claude/rules/` "apply to every project on your machine"; on conflict between user and project rule "Claude may follow either one".
- AGENTS.md: read natively when no CLAUDE.md is present (v2.1.277+), otherwise `@AGENTS.md` import or symlink. Compaction: root CLAUDE.md and unscoped rules are "Re-injected from disk", but "Path-scoped rules and nested CLAUDE.md files load into message history when their trigger file is read, so compaction summarizes them away with everything else" — https://code.claude.com/docs/en/context-window#what-survives-compaction
- Best practices — https://code.claude.com/docs/en/best-practices : "Keep it concise. For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" Include list contains "Architectural decisions specific to your project". Failure pattern: "The over-specified CLAUDE.md. If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise. Fix: Ruthlessly prune. ... delete it or convert it to a hook." "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens."
- Hooks guide — https://code.claude.com/docs/en/hooks-guide : "Hooks are user-defined shell commands. Claude Code runs them at specific points in its lifecycle, which gives you deterministic control: certain actions always happen rather than relying on the LLM to choose to run them. Use hooks to enforce project rules".

**OpenAI Codex** — https://learn.chatgpt.com/docs/agent-configuration/agents-md (developers.openai.com/codex/guides/agents-md redirects here)

- "Codex reads AGENTS.md files before doing any work." Chain: `~/.codex/AGENTS.override.md` or `AGENTS.md`, then project root down to cwd, one file per directory (`AGENTS.override.md`, `AGENTS.md`, then `project_doc_fallback_filenames`). "Files closer to your current directory override earlier guidance because they appear later in the combined prompt."
- Cap: "stops adding files once the combined size reaches the limit defined by project_doc_max_bytes (32 KiB by default)." Source: `DEFAULT_PROJECT_DOC_MAX_BYTES: usize = 32 * 1024` in https://github.com/openai/codex/blob/main/codex-rs/config/src/config_toml.rs ; truncation in https://github.com/openai/codex/blob/main/codex-rs/core/src/agents_md.rs emits only `tracing::warn!` (no user-visible warning).
- Memories — https://learn.chatgpt.com/docs/customization/memories : off by default; "Keep required team guidance in AGENTS.md or checked-in documentation. Treat memories as a helpful recall layer, not as the only source for rules that must always apply." Files under `~/.codex/memories/` are "generated state ... don't rely on editing them by hand as your primary control surface". Two-stage: per-thread extraction then global consolidation (`memories.consolidation_model`, `max_raw_memories_for_consolidation` default 256). [unverified] No `MEMORY.md` filename or skill consolidation appears in the official pages.

**pi (badlogic/pi-mono)** — https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/README.md

- "Pi loads `AGENTS.md` (or `CLAUDE.md`) at startup from: `~/.pi/agent/AGENTS.md` (global), Parent directories (walking up from cwd), Current directory." "If a directory contains `AGENTS.override.md`, Pi loads it instead ... All matching files are concatenated." `--no-context-files` disables. `.pi/SYSTEM.md` / `APPEND_SYSTEM.md` replace/append the system prompt.
- [unverified] The README does not mention `@`-imports, path-scoped rules, or just-in-time nested loading; absence inferred from the README only.
- Zechner on what pi injects: "The only thing that gets injected at the bottom is your AGENTS.md file. Both the global one that applies to all your sessions and the project-specific one" — https://mariozechner.at/posts/2025-11-30-pi-coding-agent/

**DeepSeek Harness (DSH)** — https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/context/agent-instructions/README.md

- Loader `dsh-agent-instructions`: "The first request includes one durable baseline message with the user-global `$DSH_HOME/AGENTS.md` followed by the project chain — every existing candidate file from the project root down to the session working directory, in broad-to-specific order." Candidates `AGENTS.md`, `CLAUDE.md`; overlays `AGENTS.local.md`, `CLAUDE.local.md`. "`dsh-base` already includes it with a 65,536-byte budget". Nested files are discovered just-in-time: "After a successful `read`, `write`, or `edit` call reaches a deeper directory, the next request includes the newly applicable instruction file". Over budget: "it drops whole broader files before truncating the most-specific file, and emits a visible `Workspace instruction budget ...` notice".
- The `.agents/notes/` tree is not auto-loaded by this package; it is reached by links from AGENTS.md (see 2.2).

**Cursor** — https://cursor.com/docs/context/rules : `.cursor/rules/*.mdc` (plain `.md` ignored: "A plain .md file in .cursor/rules is ignored by the rules system because it has no frontmatter"), four modes (Always Apply / Apply Intelligently / Apply to Specific Files / Apply Manually), "Keep rules under 500 lines", "Reference files instead of copying their contents", AGENTS.md accepted as "Simple alternative to .cursor/rules". "AI guidance should not be your only security control." `.cursorrules` was "Still supported, but deprecated" (Wayback 2025-07-24: https://web.archive.org/web/20250724183231/https://docs.cursor.com/context/rules).

**GitHub Copilot** — https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions : `.github/copilot-instructions.md` plus `.github/instructions/*.instructions.md` with `applyTo:` globs; nearest AGENTS.md wins; generator prompt says "Instructions must be no longer than 2 pages."

**Gemini CLI** — https://geminicli.com/docs/cli/gemini-md/ : GEMINI.md hierarchy (global, workspace, "Just-in-time (JIT) context files" when a tool touches a directory), `@file.md` imports, `/memory show`.

**AGENTS.md spec** — https://agents.md : "A simple, open format for guiding coding agents, used by over 60k open-source projects." "No. AGENTS.md is just standard Markdown." "The closest AGENTS.md to the edited file wins; explicit user chat prompts override everything." Stewarded by "the Agentic AI Foundation under the Linux Foundation".

**Native `docs/decisions` support: none found.** None of Claude Code, Codex, pi, DSH, Cursor, Copilot, Gemini CLI, or the AGENTS.md spec reads an ADR/decisions folder on its own. The only vendor routes into such a folder are Claude Code `@` imports / `.claude/rules/`, Gemini `@` imports, and links the model chooses to follow.

**Cross-harness intersection for this user (Claude Code + Codex + pi + DSH):** the only file all four load unprompted is a root-to-cwd chain of `AGENTS.md` (Claude Code only when no `CLAUDE.md` exists, else via `@AGENTS.md` or a symlink — DSH itself ships `CLAUDE.md` as a symlink to `AGENTS.md`, see 2.2) plus a per-harness user-global file (`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, `~/.pi/agent/AGENTS.md`, `$DSH_HOME/AGENTS.md`). Budgets differ: Codex 32 KiB combined (silent), DSH 64 KiB (visible notice), Claude Code 4 MiB skip with a 150k-char warning (see 3.1), pi none stated. `.claude/rules/` with `paths:` and `@` imports are Claude-Code-only.

### 2.2 DSH's Agent Notes: the most developed agent-first decision-record convention found

Repo: https://github.com/deepseek-ai/deepseek-harness (created 2026-08-13, 232,556 stars, pushed 2026-09-17 per `gh api repos/...`). Convention doc: https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/README.md

- Definition: "An **Agent Note** records a decision or proposal that affects this codebase — the *why* and *what we gave up*, the parts code and docs can't carry." Sibling `AGENTS.md` (https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/AGENTS.md): "Agent Notes are effectively RFCs written by agents: durable proposals and decision records that preserve rationale, alternatives, consequences, and required verification."
- Layout: path `{lifecycle}/{class}/yyyy-mm-dd-topic-title.md`. Lifecycle folders `proposed/`, `implemented/`, `rejected/`, plus a frozen `archived/{class}/`. Class is a closed set: `feature`, `bug-fix`, `simplification`, `architecture`, `process`, `testing` ("the classification gate rejects other folders"). "The date in the filename is when the topic was **first proposed** (per git history)." Cross-references "use relative markdown links ... never bare prose or numbers — so they are mechanically checkable and survive moves between folders."
- No index: "Do not add a centralized `INDEX.md`" — rationale note https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/process/2026-07-19-remove-generated-agent-note-index.md : "Every branch that adds, moves, or renames an otherwise unrelated Agent Note rewrites the same generated file, making that artifact a predictable merge hotspot." "The lifecycle/class filesystem tree is the Agent Note inventory."
- Implemented notes are kept current, not append-only: "is **kept current with what actually shipped** ... (facts only — paths, names, structure — not the decision itself)". "An Agent Note is never edited into a *different decision*: supersede it with a new one". https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/AGENTS.md : "Rewrite stale facts in place; do not append change history." "A reversal of the decision or its rationale requires a new Agent Note and cross-link".
- Format is machine-gated: header `# Agent Note: <title>` + `Status: proposed|implemented|rejected — <why>`; body opens with `## Problem`; implemented notes require `## Decision`, `## Alternatives considered`, `## Consequences`, and the gate rejects proposal-era headings ("`## Proposal`, `## Plan`, `## Migration plan`, and `## Acceptance criteria` may not appear in an implemented Agent Note"). "Every Agent Note carries an `## Alternatives considered` section ... A decision recorded without what it beat invites re-litigation — the failure Agent Notes exist to prevent." Enforced by `pnpm run verify-agent-note-format` (`scripts/verify-agent-note-format.ts`), part of `doc-sync`.
- When to write: "Add or update an Agent Note in the same PR only for lasting decision rationale that code, tests, and existing documentation do not explain." Root AGENTS.md rule: "**Create Agent Notes only for durable decision rationale;** mechanical/local edits are exempt".
- Archive: "Once sealed, every archived triplet is permanently frozen. Do not edit, translate, reformat, update, move, or delete it, and do not treat it as authority for current behavior." Every new note "triggers a supersession check" via the `dsh-archive-agent-notes` skill.
- Scale (my count via `gh api git/trees`, English `.md` only): implemented 422 (architecture 149, feature 110, process 61, bug-fix 53, testing 25, simplification 24); archived 634; proposed 30; rejected 14 — roughly 1,100 notes, each with a `.zh.md` twin and an `.i18n.yaml` sidecar.
- **How the agent reaches them:** the root `AGENTS.md` (https://github.com/deepseek-ai/deepseek-harness/blob/master/AGENTS.md) carries the *rule* as one bold line and links the *rationale*: e.g. "**Prefer maintained dependencies over hand-rolling** when they genuinely delete owned code and tests ([policy](.agents/notes/implemented/process/2026-07-26-dependencies-over-hand-rolling.md))." and "**Ban `prove` + `nance`** ([rule](.agents/notes/implemented/process/2026-08-26-ban-ambiguous-origin-label.md))." Nested `AGENTS.md` files (`packages/schedule/AGENTS.md`, `docs/AGENTS.md`, `.agents/notes/implemented/AGENTS.md`) load just-in-time when the agent works under them. `CLAUDE.md` at root and inside the notes tree is a symlink whose content is the string `AGENTS.md`.
- **DSH's own evidence that prose does not hold:** uniform-format note https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/process/2026-07-05-uniform-agent-note-format.md — "**Convention without a gate** (write the contract down, enforce by review) — rejected: the slop checklist already outlawed spec-speak in `implemented/` by convention, and nineteen files show what convention alone achieves here." Doc-tiers note https://github.com/deepseek-ai/deepseek-harness/blob/master/.agents/notes/implemented/process/2026-07-04-doc-tiers-and-budgets.md — "a prose rule with no mechanical backstop demonstrably does not hold here, and this repo's own quality-gates stance says invariants worth keeping are worth encoding." Same note on skills vs always-loaded files: "a standard packed into SKILL.md is invisible to an agent that edits docs without invoking the skill, and `docs/AGENTS.md` already loads as subtree instructions for anyone working under `docs/`."
- Spread: GitHub code search for `path:.agents/notes/implemented extension:md` returns ~17k file hits, but the sampled repositories are all DSH forks/derivatives (peiyuwang54/deepseek-harness-cli, zhu1090093659/dsh-trading, fufankeji/deepseek-harness-studio, ...). No independent adopter of the convention was found [sample of first 100 hits only].

### 3.2 Measurements

## 4. HTML / page-based decision docs vs Markdown-in-repo

- Every tool that renders decision records as HTML treats Markdown in the code repo as the source and HTML as a projection: log4brains https://github.com/thomvaill/log4brains — "Docs-as-code: ADRs are written in markdown, stored in your git repository, close to your code" (default `./docs/adr`), published "automatically as a static website"; last release v1.1.0 on 2024-12-17, last push 2024-12-17 (`gh api`) — effectively dormant. Backstage ADR plugin https://github.com/backstage/community-plugins/blob/main/workspaces/adr/plugins/adr/README.md — repo `catalog-info.yaml` annotation `backstage.io/adr-location: docs/adrs` points at "the directory which contains your ADR markdown files"; the portal renders and indexes them. DSH's `website/` is described in its root AGENTS.md as a "VitePress documentation projection" and `website/AGENTS.md` says to "Keep documentation content out of the" website tree [truncated in search snippet].
- Separate git store: the only precedent found for decision-adjacent documents living in a git repo *other than* the code repo is humanlayer's `thoughts/` (Markdown, separate repo, symlinked in, commit-blocked in the code repo; read by a locator subagent on demand) — https://github.com/humanlayer/humanlayer/blob/main/hlyr/src/commands/thoughts/init.ts . It is Markdown, not HTML.
- Agents reading HTML pages: no harness auto-loads a rendered page. Claude Code can read a published artifact on explicit instruction (the Artifact tool's `read` action in this session's own tool surface; Claude-Code-only, on demand) [observed in the tool description available to this session, not a public doc]. Codex, pi and DSH would need a web-fetch tool call and a URL in their prompt. Nothing found where a team keeps decisions as HTML pages in a separate store *and* an agent consumes them routinely.
- **Verdict: no precedent found** for HTML-as-source decision records outside the code repo being read by coding agents. All observed practice is Markdown next to the code (or a Markdown sibling repo), with HTML only for humans.

## 6. Dominant vs rare

**Dominant (2025-2026):**
1. One short root instruction file (`AGENTS.md`, ~967k files; `CLAUDE.md`, ~780k) concatenated root-to-cwd and auto-loaded by every harness — with every vendor warning it is advisory and must stay short (Anthropic 200 lines, Cursor 500, Codex 32 KiB, Copilot "2 pages"). Decisions that must bind are written *there* as one-liners; Anthropic lists "architectural decisions" as CLAUDE.md content, and ~20% of CLAUDE.md files contain the word "decision".
2. Classic ADRs in `docs/adr` remain the dominant *human* decision store (~627k files) but are mostly not wired to agent files (~1.5% cross-mention).
3. Dated plan/research files read on demand (humanlayer, superpowers, Anthropic progress files, Every) — widespread among practitioners, always with an explicit retrieval step, never auto-injected.
4. Mechanical rules moved out of prose into hooks/linters — the consensus recommendation from Anthropic docs, the Claude Code maintainer, HumanLayer, zernie, DSH, and HN threads.

**Rare:**
- A gated, path-encoded decision-record tree with rule-in-AGENTS.md + rationale-in-note (DSH; ~1,100 notes; no independent adopter found).
- Separate git repo for agent documents (humanlayer `thoughts/`).
- Issue-tracker-as-memory (Beads), agent-selected rules (Cursor "Apply Intelligently"), ranked trust orders across files (Gadfly).
- ADR-to-agent bridges (archgate, adr-kit, Mneme, Decision Guardian, AgDR, the two Claude Code skills in joelparkerhenderson/architecture-decision-record): real but all under ~70 stars and none vendor-endorsed.
- HTML decision pages consumed by agents: none.

## 7. Options for a solo developer running Claude Code + Codex + pi + DSH

Goal: one place where decisions are recorded *and* become binding on every harness. The evidence splits this into two problems that no single artifact solves: (i) recording so both humans and agents find it, (ii) binding, which prose cannot do on any harness (3.1, 3.2) and which each harness enforces differently.

**Option A — Rule line in the shared `AGENTS.md` chain, rationale in a Markdown decision note next to it (DSH pattern).**
Record: `docs/decisions/` or `.agents/notes/` with `YYYY-MM-DD-topic.md`, `Status:`, `## Problem / ## Decision / ## Alternatives considered / ## Consequences`. Bind-ish: the *rule* is one bold line in `AGENTS.md` linking the note; `CLAUDE.md` is a symlink to `AGENTS.md` (DSH does this; Claude Code also falls back to AGENTS.md when no CLAUDE.md exists). All four harnesses load that chain unprompted (2.1). Keep the root file under Codex's 32 KiB and DSH's 64 KiB; put subtree rules in nested `AGENTS.md` (Codex, DSH, Claude Code load nested files just-in-time; pi does not per its README [unverified]). Precedent: DSH (2.2), Anthropic's own "architectural decisions" guidance, Nygard/MADR for the note shape. One design choice has two precedents that disagree: Nygard/AWS/Fowler make an accepted record immutable ("it should never be reopened or changed - instead it should be superseded"), while DSH keeps implemented notes' *facts* current in the same PR and only forbids editing the *decision* ("Rewrite stale facts in place; do not append change history."). DSH's variant exists because agents re-read notes as current authority and stale paths mislead them [DSH's stated rationale, 2.2]. Evidence: specific rule lines are followed (ETH); linked rationale is one hop away for humans and for the model when it chooses to follow the link. Known failure: length and compaction decay; the note itself is never auto-read.

**Option B — Same records, fanned out by a sync tool instead of symlinks.**
Keep one source (`.agents/` or `.ruler/`) and let ruler / rulesync / ai-rulez / dotagents write `CLAUDE.md`, `AGENTS.md`, `.cursor/rules`, etc. Precedent: ruler lists Claude Code, Codex and Pi as targets (3.3); DSH is not a ruler target [no precedent found for DSH], but DSH reads `AGENTS.md`, so the AGENTS.md output covers it. Adds nothing over Option A for these four harnesses except when per-harness wording must differ.

**Option C — Claude-Code-native layering (`.claude/rules/` with `paths:`, `@docs/decisions/...` imports).**
Best fit for Claude Code alone; Codex, pi and DSH ignore `.claude/rules/` and `@` imports (2.1). Precedent: Anthropic memory docs. Not a cross-harness answer on its own; usable as a Claude-only refinement layered on A.

**Option D — Decision -> executable check, with the record cited in the check's message.**
For any decision that is mechanically checkable (banned dependency, file layout, commit format, forbidden command), write the check (PreToolUse deny hook, ast-grep rule, dependency-cruiser rule, CI gate) and have its failure text link the decision note. Precedent: Anthropic docs and maintainer statement (hooks), zernie / HumanLayer ("Never send an LLM to do a linter's job"), DSH `verify-*` gates and its explicit rejection of "Convention without a gate", ThoughtWorks fitness functions, Decision Guardian for ADR-on-PR. Cross-harness: each harness has its own hook surface (Claude Code hooks; Codex hooks; DSH `packages/hooks` "Claude Code/Codex bridges"; pi extensions), so the *check* must be compiled per harness. Third-party precedent covers only part of the set: archgate (Claude Code/Cursor/VS Code/Copilot CLI/opencode) and adr-kit (Claude Code/Codex/Copilot CLI/OpenCode) turn ADRs into agent-side rules or hook injections; neither targets pi or DSH, and none was found for all four [negative result]. A repo-level linter/CI gate (ast-grep, dependency-cruiser, a `verify-*` script as in DSH) is the harness-independent fallback, since all four harnesses run shell commands and the check fires regardless of which agent made the edit.

**Option E — Agent-owned memory layers (Claude auto memory, Codex memories).**
Not a place for binding decisions: machine-local, per-harness, budget-truncated, and Codex says "not ... the only source for rules that must always apply"; Codex #39223 shows a stale memory overriding an explicit rule. Precedent as a *supplement* only.

**Option F — Decision records as HTML pages (Artifacts) in a separate git store.**
No precedent found for agents consuming these (section 4). Humans can read them; agents will not unless a prompt hands them a URL and the harness has a fetch tool. If kept, the Markdown source must also exist in the repo and the page must be a projection (log4brains/Backstage pattern), otherwise the record is invisible to every harness.

**Option G — Issue tracker as memory (Beads-style `bd remember`).**
Precedent exists (Beads) but with heavy critique and no cross-harness auto-load; each harness must be told to run the CLI.

**Net reading of the evidence:** the one-place requirement is met by a Markdown decision note in the repo plus a one-line rule in the shared `AGENTS.md` chain (A); the binding requirement is met only by D for the subset of decisions that can be mechanized, and by nothing for the rest — every source that measured it (Anthropic docs, ETH, Khatri, the issue trackers, DSH's own notes) says prose is followed often but not reliably, and that reliability falls with length and session age.
