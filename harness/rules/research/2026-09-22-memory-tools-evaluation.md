# Persistent memory layers for AI coding agents — how the industry evaluates them (2026-09-22)

Scope: cross-session memory for coding agents (facts/observations stored across sessions and retrieved later). Sources: vendor docs, arXiv, vendor blogs, GitHub issue trackers (via authenticated `gh api`), HN, practitioners' own sites, plus measurements taken on this machine's own claude-mem install. Every claim carries a URL. Quotes are verbatim unless marked. Inferences are marked `[unverified]`.

Method caveats that apply to the whole document:
- WebSearch was exhausted (200/200) for this session, so everything came from direct fetches of known URLs, raw GitHub content and `gh` queries. Where a page could not be fetched, that is stated rather than guessed.
- WebFetch summarizes pages through a small model. Quotes taken from vendor *docs*, arXiv abstracts and GitHub issue bodies were spot-checked against the raw text (issue bodies via `gh api`). Quotes taken from long-form transcripts (Karpathy) and some blog posts were only obtained through the summarizer and are marked `[WebFetch-paraphrase]`.
- Negative evidence was collected with the same effort as positive; issue trackers are structurally biased toward complaints, and vendor pages toward praise. Both biases are called out where they matter.

**What each school argues, in one line each.** School (a) vendors argue from context economics: the file system is unbounded, restorable, inspectable, and lets retrieval be just-in-time (Anthropic, Manus, Zechner). School (b) vendors argue from recall benchmarks on chat transcripts (LoCoMo/LongMemEval) and from token-per-retrieval counts (Mem0, Zep, Supermemory). **Zero vendors in either school publish an ablation isolating "memory on vs off" on a coding task**, with the partial exceptions of Anthropic's bundled 39% (agentic search, memory + context editing) and Supermemory's self-reported SWE-ContextBench / "Markdown memory" comparison.

### The Mem0 numbers dispute

- **Mem0 paper** (https://arxiv.org/abs/2504.19413, 28 Apr 2025): "26% relative improvements in the LLM-as-a-Judge metric over OpenAI", "91% lower p95 latency", ">90% token cost" savings; graph variant "around 2% higher".
- **Zep rebuttal** (Daniel Chalef with Preston Rasmussen, 6 May 2025, https://blog.getzep.com/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/): Zep reports itself at "75.14% +/- 0.17" J score vs Mem0's report of Zep at 65.99%; p95 search "0.632 seconds" vs Mem0's reported 0.778s. Three implementation errors alleged: both speakers given the user role; timestamps appended to message text instead of `created_at`; searches run sequentially, "artificially inflating Zep's reported search latency". Plus the LoCoMo-dataset critique summarized above.
- **Letta's reproduction** (https://www.letta.com/blog/benchmarking-ai-agent-memory): Mem0 graph 68.5% vs Letta filesystem 74.0% (GPT-4o mini); "The quality of an agent's memory often depends more on the underlying agentic system's ability to manage context and call tools than on the memory tools themselves"; Mem0 "did not respond to requests for clarification".
- **Reproduction failures on Mem0's own tracker** (`gh search issues --repo mem0ai/mem0 "locomo"`): #2800/#3944 "unable to reproduce locomo eval scores", #2967 "Unable to reproduce ZEP baseline results", #3667 "results worse than paper", #3789 "Question About Open-Domain Results (Table 1)".
- **Judge-prompt sensitivity** (https://github.com/mem0ai/mem0/issues/7235, by Mnemoverse.AI, a competing vendor, conflict disclosed): re-scoring Mem0's published LoCoMo-10 answers — Mem0's own judge prompt 91.0%; a "strict" prompt 35.0%; unmodified LongMemEval rubric 81.7%; human-calibrated judge 85.3%; "863" answers flipped. The paper "The Judge Is the Benchmark" is described as forthcoming — `[unverified]` as a published preprint.
- **No Mem0 rebuttal to Zep located**: the https://mem0.ai/blog index (fetched 2026-09-22) shows no such post. Treat as "not found", not "confirmed absent".
- **Production audit** (https://github.com/mem0ai/mem0/issues/4573, closed, +6, 24 comments, 2026-03-27): "224 entries survived the full process. Out of 10,134. That's 97.8% junk across the entire collection." Per-batch junk rates 95.4%–98.5% with `gemma2:2b` extraction; the reporter later switched to Claude Sonnet 4.6 (body truncated in fetch for those rows). Junk classes: system-prompt restating, heartbeat/cron noise, architecture dumps, transient task state, "668 copies of a single feedback-loop hallucination". This is the single most concrete piece of evidence on extraction-store quality in production, but it is one deployment with a weak extractor for most of the window.

### Are any benchmarks about coding agents?

**No benchmark ports the LoCoMo/LongMemEval "multi-session, long-gap, recall project facts later" paradigm to a coding agent.** Checked: arXiv searches for memory + coding agent + SWE-bench and cross-session memory + software engineering agent; Terminal-Bench leaderboard (https://www.tbench.ai/leaderboard renders client-side; no row data retrievable); vendor pages. What does exist is adjacent:

- **SWE-Bench-CL** (https://arxiv.org/abs/2507.00014): continual learning across chronologically ordered SWE-Bench-Verified issues per repo, with a FAISS memory module and forgetting/transfer metrics — the closest thing to "memory across a sequence of coding tasks".
- **CODESKILL** (https://arxiv.org/abs/2605.25430): RL-trained skill bank; "improves average pass rate by 9.69 [points] over the no-skill baseline and by 4.01 over the strongest prompt-based or memory baseline" on EnvBench, SWE-Bench Verified, Terminal-Bench 2 — one of the few explicit memory-vs-no-memory ablations.
- **SWE-Exp** (https://arxiv.org/abs/2507.23361): experience bank of successful and failed trajectories; "73.0% Pass@1 resolution rate on SWE-Bench Verified using Claude 4 Sonnet"; no explicit no-memory delta in the abstract.
- **ReasoningBank** (https://arxiv.org/abs/2509.25140): distills strategies from successes and failures; "consistently outperforms existing memory mechanisms that store raw trajectories or only successful task routines" on web and SWE tasks; exact SWE numbers not in the abstract.
- **Repository memory for localization** (https://arxiv.org/abs/2510.01003): commit history as non-parametric memory improves LocAgent on SWE-bench-Verified/Live — genuinely persistent repo-level memory, localization only.
- **Decision-Aware Memory Cards** (https://arxiv.org/abs/2606.08151): "On 50 SWE-bench Verified file-retrieval instances, ... reranking improves hit@1 from 0.58 to 0.78" — retrieval compression, not persistence.
- **Supermemory SWE-ContextBench** (vendor, https://supermemory.ai/): "55.95%" F2P / "30.30%" resolution; methodology not independently examined.
- Calibration points outside coding: Agent Workflow Memory (https://arxiv.org/abs/2409.07429, +24.6%/+51.1% relative on Mind2Web/WebArena), Dynamic Cheatsheet (https://arxiv.org/abs/2504.07952, math/logic).

Pattern: every positive coding result is about **reusable procedures/strategies mined from trajectories** (skills, experience banks, commit history), not about **stored facts about the user or project recalled days later**. That distinction matters for the verdict: the measured wins map onto "skills/AGENTS.md/plan files", not onto "observation store".

### Reading of the balance

Every quantified claim collected points to cost (+64% spend, 10–20× observer blowups, 11–16k tokens of preamble even when opted out, 34% of a subagent's first turn), correctness (newest corrections silently dropped, stale world-model with no freshness signal, cross-project leakage, 97.8% junk extraction, 31% extraction failures) or security (Codex exfiltration report, three vendors warning about secrets). The helps side is either bundled (Anthropic's 39%), non-coding (LoCoMo/LongMemEval), self-reported (Mem0, Supermemory), or about skills/procedures rather than stored facts (CODESKILL, ReasoningBank, SWE-Exp). The failure classes recur identically across three unrelated projects (claude-code, codex, claude-mem): silent staleness, silent truncation, silent token inflation, cross-context leakage. That convergence is the strongest empirical signal in this survey.

### Measurements on this machine (claude-mem 12.4.9, installed 2026-04-30; `~/.claude-mem/`)

These are local facts, not published evidence, but they are the only measured data in this document that were not produced by an interested party.

- Store size: `claude-mem.db` 848 MB + `chroma/` 465 MB ≈ 1.3 GB for 4.7 months.
- Contents: 10,681 observations across 16 projects (2026-05-04 → 2026-09-22), 2,205 session summaries, 361 SDK sessions; 11.8 M chars of narrative+facts (~3 M tokens). The `relevance_count` column is 0 for all 10,681 rows. So ~10.7k observations were written and, outside the automatic 50-observation preamble, essentially never read back.
- Injection: running the SessionStart context hook for this worktree returns 7,449 chars (~1.9k tokens by chars/4; 96 lines) — a title index of the 50 most recent observations plus the last session summary. The header says "Stats: 50 obs (15,851t read) | 569,042t work | 97% savings". The "savings" figure is `1 − read/work` where `work` = `discovery_tokens` (sum on this DB: 301 M, mean 28,190 per observation), i.e., the raw tool output that was summarized. ## 7. Verdict for a solo developer running Claude Code + Codex + pi + DSH

**Rely on files (AGENTS.md / CLAUDE.md, a memory directory of topic files, plan/progress files in the repo), keep Claude Code's own auto memory with periodic pruning, and do not run a cross-harness observation store. Uninstall or at minimum disable claude-mem's capture hooks.** Reasons, in order of evidentiary weight:

1. **No benchmark measures the thing an observation store sells for coding.** The only benchmarks with numbers are chat-transcript QA (LoCoMo, LongMemEval), and MemoryArena shows LoCoMo-strong systems "perform poorly" on agentic tasks. The coding results that do exist (CODESKILL +9.69, SWE-Exp, ReasoningBank, commit-history memory) all reward *reusable procedures and repository artifacts* — the AGENTS.md / skills / plan-file form — not recalled per-session facts.
2. **The vendors closest to the problem moved toward files.** Anthropic's API memory tool and Claude Code auto memory are files with just-in-time reads; Codex consolidates into `MEMORY.md`/`skills/`; Letta's own filesystem agent beat Mem0 on LoCoMo and its new product is a git-backed file store; Manus calls the file system "the ultimate context". Devin Knowledge and Windsurf memories — the two shipped auto-memory products at Cognition — are being retired in favour of skills/rules. DSH ships no memory and explicitly disclaims the reference MCP servers it bridges to.
3. **Every measured number in the hurts column is about the extraction-store pattern or about unbounded auto-injection.** +63.9% spend and 10× observer amplification (claude-mem), 97.8% junk (Mem0 audit), 31% extraction failures (Codex), hallucination propagation at extraction (HaluMem). Those are the mechanics of school (b). School (a)'s measured problems (11–16k preamble, overflow dropping newest entries, subagent leakage) are real but bounded by a 25 KB file and fixable by pruning — which is what Osmani and the #91473 user do.
4. **Local evidence on this machine is decisive for this user**: 10,681 observations written, 13 explicit reads in 4.7 months, `relevance_count` 0 everywhere, 1.3 GB on disk, ~12.9k Sonnet compression calls on subscription quota, and near-duplicate decisions in the injected index. The 97% "savings" banner is a counterfactual, not a saving. The only thing the plugin demonstrably delivers each session is a ~1.9k-token recent-title index — which `git log`, the plan files, and the auto-memory index already provide.
5. **Cross-harness is not where the evidence points.** The four harnesses in question already share a file-based lowest common denominator (AGENTS.md/CLAUDE.md read by Claude Code, Codex, pi and DSH; Codex and Claude both consolidate into `MEMORY.md`-shaped files). A shared store would have to beat "one repo-tracked notes directory readable by all four", and no vendor has published a coding-task result that does. Practitioners with cross-harness setups (Zechner, Horthy, Ball) chose files.

What this verdict rests on: the arXiv abstracts and benchmark papers cited; Zep's rebuttal and Letta's reproduction; verified GitHub issue bodies with measured numbers (`gh api`, 2026-09-22); vendor docs quoted verbatim; local SQLite/log measurements on this machine.

What it lacks:
- **No controlled A/B on a coding workload** for any tool, vendor or independent. Nobody has measured "same developer, same tasks, memory on vs off, outcome + tokens". The strongest evidence here is convergent failure reports plus local usage counts, not an experiment.
- **Positive testimony is structurally under-sampled**: issue trackers do not record "it quietly helped"; the practitioner sample is nine people; HN comments are anecdotes.
- **Vendor numbers were not reproduced here**; Supermemory's "81% vs 69% vs Markdown memory" and its SWE-ContextBench figure are the only direct file-vs-store coding claims found, and they are unaudited.
- **Unfetched**: ChatGPT memory FAQ (403), BEAM origin paper, Mem0's "97% Claude Code footprint" post, Cursor Memories' current status, the "Judge Is the Benchmark" preprint, Terminal-Bench leaderboard rows, Steinberger's own view of OpenClaw memory.
- **Local measurement caveats**: retrieval counts come from PostToolUse hook logs and would miss reads that bypass the MCP tools (e.g., the `mem-search` skill shelling out, or the web viewer); `relevance_count` may simply be unwired in v12.4.9 rather than reflecting zero use; the token estimate for the injected index is chars/4.

If the user wants a cheap experiment before uninstalling: keep claude-mem's MCP search tool but disable the PostToolUse/Stop capture hooks for 30 days and count how often `search`/`get_observations` are invoked and whether any invocation changed an outcome; the current baseline is 13 calls in 4.7 months.
