# omp (oh-my-pi) hook/config surface — measured on this machine

Installed: `omp --version` → `18.0.4` (Homebrew tap `can1357/tap/omp`, binary
`/opt/homebrew/bin/omp`, a Bun-compiled single-file executable —
`$bunfs/root/omp-darwin-arm64` shows up in its own stack traces). Upstream
`package.json` (`can1357/oh-my-pi`, `main`, fetched via `gh api`) pins its own
workspace catalog to `18.2.8`, so the local install is one minor behind
upstream. The shell `omp` is a wrapper function (not the raw binary) that
injects `--no-extensions -e ~/.omp/agent/extensions/yoki-bridge.ts` unless
`YOKI_OMP_ALL_EXTENSIONS=1`; every command below that needed the *native*
surface (not yoki's) called `/opt/homebrew/bin/omp` directly.

Sources used: `omp --help` / `omp help`, the repo's `docs/*.md` fetched raw
from `github.com/can1357/oh-my-pi@main` via `gh api repos/.../contents/docs`
+ `raw.githubusercontent.com`, the installed `~/.omp/agent/*` files (read-only),
and the production extension `domains/dev/config/omp/extensions/yoki-bridge.ts`
(symlinked into `~/.omp/agent/extensions/`), which is TypeScript typed against
the real `@oh-my-pi/pi-coding-agent` `ExtensionAPI`/`ExtensionContext` and is
what actually drives omp today — it is itself a primary source, not a
description of one.

**Verification limitation**: the plan called for registering a throwaway hook
in an isolated `--profile` and capturing one live headless tool-call payload.
The hook was written and an isolated profile (`yoki-research-scratch`) was
created and exercised, but every attempt (`omp --profile yoki-research-scratch
-p ... --model haiku`, then retried against the default profile's stored auth
with `--no-session`) failed at credential resolution — `error: No API key
found for anthropic. Use /login, set an API key environment variable, or
create ~/.omp/agent/agent.db` — because this tool's Bash subprocess has no
provider env vars and no access to whatever keychain/login state the user's
interactive shell has (a `security find-generic-password` probe to check was
itself blocked by the auto-mode classifier as credential exploration, which is
correct — I did not pursue it further). So the `tool_call`/`tool_result`
payload shape below is confirmed from the docs' own field lists
(`hooks.md`, `extensions.md`) and from `yoki-bridge.ts`'s working, in-production
consumption of `payload.toolName` / `payload.input` — not from a byte-for-byte
captured JSON blob. The isolated profile and its hook file were deleted
(`~/.omp/profiles/yoki-research-scratch` removed via `/bin/rm -rf`).

## 2. Permissions / approvals

| What | Shape | Source | Verified how |
|---|---|---|---|
| Approval tiers | Every tool declares `read` \| `write` \| `exec` (or a function `(args) => tier`). Undeclared/malformed → treated as `exec` (fail-safe default). MCP tools are always `write`. | `docs/approval-mode.md` lines 3-12 | Read raw doc |
| `tools.approvalMode` values | `always-ask` (auto: read only), `write` (auto: read+write), `yolo` (auto: everything — **the schema default**). `--auto-approve`/`--yolo` force `yolo` for the session; `--approval-mode=<value>` overrides `tools.approvalMode` per-session. | `docs/approval-mode.md` lines 14-24; `omp --help` (`--approval-mode`) | Read doc + help output |
| This machine's config | `~/.omp/agent/config.yml`: `tools.approvalMode: yolo`, plus a large `tools.approval` block (`eval: prompt`, `read/grep/todo/task/web_search: allow`) and a `bash.patterns` allow/deny list (destructive commands denied, read-only git/gh/fs commands allow-listed). This file is generated by yoki's own `lib/targets/gen.js --target omp`; the header note says `symbolPreset`/`composer`/`theme`/`setupVersion` are the only keys omp itself writes back and are therefore carried forward by the generator rather than overwritten. | `~/.omp/agent/config.yml` (read) | Read file directly |
| Precedence between tool-declared policy, user policy, and mode | 6-step resolution: (1) tool's own `approval(args)` tier; (2) tool `policy:deny` or user `deny` always wins; (3) in `yolo`, an explicit tool `allow`/`prompt` policy wins over user policy, `override` alone does **not** force a prompt; (4) in non-yolo, `override:true` only allows via an accompanying tool `policy:allow`, otherwise prompts; (5) explicit tool policy beats user policy; (6) otherwise the active mode's tier table decides. | `docs/approval-mode.md` lines 45-54 | Read raw doc |
| `bash.patterns` scope | Pattern rules gate the `bash` tool only — they do **not** gate the `eval` tool, which also declares `exec` and can spawn a shell via subprocess. A `bash.patterns` deny does not stop the same command run through `eval`; under `yolo` that resolves to plain `allow`. Must additionally set `tools.approval.eval: prompt`/`deny` to close that gap — which this machine's config.yml already does (`eval: prompt`). | `docs/approval-mode.md` lines 64-72 | Read doc; cross-checked against local config.yml which already sets `eval: prompt` |
| Does omp have its own sandbox (bwrap/seatbelt)? | **No.** "This pattern policy controls approval for the `bash` tool; it is not process or filesystem containment. An approved command retains the shell's ambient filesystem, network, and subprocess access." And separately: "Extensions are not sandboxed (same process/runtime)"; the doc explicitly frames external sandboxing as something a *host* does: "Intended for a host that embeds the agent inside a sandbox denying [...]". | `docs/approval-mode.md` line 70; `docs/extension-loading.md` line 273; `docs/extensions.md` line 482 | Read raw docs (three independent confirmations) |
| "Ask" in headless mode | Subagents (`task`) always run with `tools.approvalMode: yolo` forced, "so ordinary tier-based prompts do not stall them." A user `tools.approval.<tool>: prompt` policy **cannot** be satisfied in a headless subagent and the call is **rejected** outright (not silently allowed, not silently denied-as-deny — a distinct "prompt in headless context" failure). `deny`/`allow` user policies still apply normally. | `docs/approval-mode.md` lines 160-163 | Read raw doc |
| Hook decision vs native approval — does a hook override the tier system? | Not documented as an explicit override relationship; they are two separate gates in different subsystems (approval tiers live in `wrapper.ts`/tool declarations, hooks live in the extension runner's `tool_call` handler which fires *before* tool execution and can `block` independent of tier). A `tool_call` hook `block:true` stops execution before the approval-tier system is even consulted for that call (see execution-flow diagram in `docs/hooks.md`), so a hook's block is effectively upstream of / stronger than approvalMode, but nothing states a hook can force-*allow* what the tier system would deny. | `docs/hooks.md` lines 127-142 (flow diagram) | Read raw doc; inference from documented flow, not an explicit precedence statement — flag as such |

## 4. Formatting/gate hooks (Claude Code parity)

| Claude Code event | omp equivalent | Basis |
|---|---|---|
| `PostToolUse(Edit)` | `tool_result` event, filtered by `toolName === "edit"` (i.e., matcher `"edit"` in yoki's own manifest translation — omp itself has no separate per-tool event, filtering happens in the handler or via yoki's `matcher` convention). Fires after the edit tool executes; handler can override `content`/`details`/`isError`. | `docs/hooks.md` lines 158-172 (payload carries `toolName`); yoki's own `yoki-hooks.json` already encodes this as `matcher: "edit"` on `tool_result`-mapped specs for `post:edit:format`/`post:edit:typecheck` |
| `Stop` | `session_stop` — "main-session stop hook, awaited before settle." Advisory `{continue:true, additionalContext}` is capped at **8 continuations**; explicit `{decision:"block", reason}` takes precedence, doesn't consume that budget, and stays blocking until the hook allows completion or the user interrupts. A refusal with no `reason` gets a diagnostic continuation instead of being honored outright. **Never fires for task/subagent sessions**, and defers until all agent-owned background async jobs are idle. | `docs/extensions.md` line 318 |

This is a materially richer contract than Claude Code's Stop hook (continuation budget, block-vs-advisory distinction, explicit subagent exclusion) — worth encoding as first-class states in jig's omp adapter rather than collapsing to a boolean.

## 5. Workflow/eval kernel (`agent()`/`workpool()` vs Claude Code's `agent()`/`parallel()`/`pipeline()`)

| Axis | omp eval kernel | Claude Code Workflow-tool primitives (for contrast) |
|---|---|---|
| Where it runs | Inside the `eval` tool's own JS/Python sandboxed kernel — **model-authored code** the LLM writes and the `eval` tool executes (Bun worker/subprocess for JS, a retained Python subprocess kernel for Python), not harness-authored orchestration. | A TypeScript script authored ahead of time (by the operator, via `workflow-authoring`), run by the harness's own Workflow tool. |
| `agent()` | `await agent(prompt, {agent?, label?, schema?, schemaMode?, isolated?, apply?, merge?, tools?})` → returns an `AgentHandle` **immediately** (non-blocking registration of a background subagent job); `.wait()`/`.done()`/`.send()`/`.cancel()`/`.output()`. Preflight (spawn policy, `task.maxRecursionDepth`, unknown `tools`) fails synchronously; execution failures surface only from `.wait()`. `agent` selector picks a pre-defined task-agent (frontmatter model always wins — **no per-call model override**). | Not directly comparable without the Workflow-tool doc in hand, but structurally it's declarative graph wiring rather than an async handle returned into arbitrary running code. |
| `workpool()` | `workpool(agent=None, name=None, context=None, tools=None)` — a **keep-alive pool** bounded by `task.maxConcurrency` (default 32). `.push(*items)` round-robins items to the lowest-context-usage idle worker or spawns new workers while there's room; `eval.workpool.freshAgents=true` instead always spawns fresh per item. No `.wait()` on the pool itself — you leave eval and poll `hub {op:"wait", ids:[pool.name]}` — because the kernel must stay free to serve `@tool` callbacks. | N/A for direct comparison. |
| Concurrency/limits | `task.maxRecursionDepth` default **2** (negative = unlimited); `task.maxConcurrency` default **32** (0 = unbounded); eval default timeout **30s** (0 disables); output sink window 50 KiB / 100 KiB live tail. | Not established in this pass. |
| Tool exposure into children | `@tool`/`tool(fn)` defines a kernel-local tool other agents can call; consumed via `task` items' `tools`, `agent(tools=...)`, `workpool(tools=...)`. Calls run on a dedicated runner thread/worker context so a parent blocked in `wait()` can still serve them. Plan mode **rejects `tools` entirely**. | Not established in this pass. |
| Sizing implication for a jig adapter | omp's `agent()`/`workpool()` are **not** a workflow-graph replacement — they're a code-execution-time concurrency primitive available only inside `eval` cells, gated by `task.maxRecursionDepth`/`maxConcurrency`/plan-mode. A jig adapter mapping Claude Code's `agent()/parallel()/pipeline()` onto omp cannot target these directly; it would have to target the `task` tool (the model-facing multi-agent dispatch surface: `{context, tasks:[{agent, task}]}`, described in `docs/task-agent-discovery.md`) instead, since that's the harness-level (not eval-sandbox-level) subagent surface. | Read `docs/tools/eval.md` in full + cross-read `docs/task-agent-discovery.md` |

## 6. Box (sandboxed execution)

| Question | Finding | Source |
|---|---|---|
| Does omp have its own OS-level sandbox? | **No.** Confirmed three separate times in the docs: (1) approval-mode.md — bash pattern policy "is not process or filesystem containment," an approved command "retains the shell's ambient filesystem, network, and subprocess access"; (2) extension-loading.md — "Extensions are not sandboxed (same process/runtime)"; (3) extensions.md — a code path is explicitly "Intended for a host that embeds the agent inside a sandbox denying [...]," i.e., omp expects an *external* sandbox, same posture jig already assumes for Claude Code and Codex. | `docs/approval-mode.md` L70, `docs/extension-loading.md` L273, `docs/extensions.md` L482 |
| Install method for a custom sbx kit | No plain `npm install`.
