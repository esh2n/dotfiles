# Multi-lane review per harness (2026-09-22)

Question: which of Claude Code / Codex / pi / omp (oh-my-pi) / DSH (DeepSeek Harness)
can natively spawn several independent reviewer agents on the same diff, in
parallel, with fresh context, and collect their findings — without a
third-party orchestration engine? Feeds a choice between three shapes:
(1) SKILL.md procedure + each harness's native subagent facility,
(2) a minimal harness-independent runner,
(3) give up parallel lanes, use each harness's native single-pass review.

## The four lenses on the category

### 1. Vendors

- **Claude Code** explicitly designs for this pattern and names review as a canonical example. The Workflow doc's own example prompt: *"use a workflow to review every file changed in this PR for correctness issues, then merge the per-file findings into one ranked summary."* It also states the quality rationale directly: moving to a workflow *"can have independent agents adversarially review each other's findings before they're reported... so you get a more trustworthy result than a single pass."* (code.claude.com/docs/en/workflows.md)
- But Claude Code's own **native, zero-setup multi-agent review is cloud-only and priced separately**: `/code-review ultra` runs "in a cloud sandbox," costs "$5 to $25 per review" after 3 free runs (0 free on Team/Enterprise), requires claude.ai sign-in, and is unavailable on Bedrock/Vertex/Foundry/ZDR orgs (code.claude.com/docs/en/ultrareview.md). It is not a candidate for a portable, five-harness local runbook.
- **Codex** ships parallelism as a stable-but-opt-in feature (`multi_agent_v2`, off by default, this machine turns it on) and its docs say plainly that skill/AGENTS.md instructions can request delegation — but its own skills doc (learn.chatgpt.com/docs/build-skills) frames skills as tool/MCP integrations and never mentions sub-agent spawning, and no Codex doc page describes "review" as a delegation use case the way Claude Code's does. Cost caveat, verbatim (WebFetch): *"Because each subagent does its own model and tool work, subagent workflows consume more tokens than comparable single-agent runs."*
- **pi**'s docs are the one clean negative: *"Pi does not have built-in mechanisms for spawning subagents, parallel agents, or multi-agent review... Pi itself remains fundamentally single-agent."* (pi.dev/docs/latest/extensions, WebFetch)
- **omp** is the vendor most explicit about this exact use case, via a first-class UX feature rather than a doc aside: the `workflowz` magic keyword's stated purpose is *"broad research, reviews, migrations, and adversarial coverage"* — review is named in the product itself, not just in an example.
- **DSH** ties itself to Claude Code's own design ("the field vocabulary matches the Claude Code dynamic-workflows meta block") rather than inventing a separate contract, and its subagent backends can literally proxy to Claude Code or Codex — DSH is architecturally the most "harness-agnostic-aware" of the five, but has no shipped review-specific command.

### 2. Practitioners

- **Simon Willison**, "Codex Subagents" (2026-03-16, simonwillison.net/2026/Mar/16/codex-subagents/): reports OpenAI's GA subagent launch, quotes the vendor example (`browser_debugger`, `code_mapper`, `ui_fixer` spawned for one investigation), and flags his own uncertainty rather than endorsing it wholesale: *"It's unclear to me what the difference between 'worker' and 'default' is."* This is commentary on the feature's existence and rough edges, not a reviewed cross-harness review procedure.
- Willison, "Moonlight & Mayhem" (2026-08-07): an anecdotal comparison where GPT-5.6 Sol Ultra's "aggressive" sub-agent use produced a better result on one task than Claude Fable 5's single-agent approach — one story, not a review-specific benchmark, and Willison notes Codex still "failed to spot and correct" a bug despite reviewing screenshots. Per the research-agent rule against single-anecdote conclusions, this neither confirms nor refutes multi-lane review specifically.
- I did not find a named practitioner who has published a cross-harness (Claude Code + Codex + pi/omp/DSH) *review* procedure specifically — Willison's posts are the closest hit and are about subagents generally, not review. This is a genuine gap, not a "no precedent" claim about the underlying pattern (see repo evidence below).

### 3. Measured evidence

- **arXiv 2603.12123, "Cross-Context Review" (CCR)** — abstract (verbatim): *"Large language models struggle to catch errors in their own outputs when the review happens in the same session that produced them. This paper introduces Cross-Context Review (CCR), a straightforward method where the review is conducted in a fresh session with no access to the production conversation history."* Design: 30 artifacts, 150 injected errors, 360 total reviews. Results: CCR F1 = 28.6%; same-session self-review (SR) F1 = 24.6% (p=0.008); repeated same-session review (SR2) F1 = 21.7% (p<0.001, rules out "just ask twice" as the mechanism); context-aware subagent review (SA) F1 = 23.8% (p=0.004).
- **What it does NOT measure**, explicitly: it is single-reviewer, sequential — it does *not* test parallel independent reviewer lanes on the same diff, simultaneous multi-agent review, or voting/aggregation across concurrent reviewers. It supports "fresh context beats same-session review" strongly (that's shape 3's whole premise); it gives **no evidence either way** on whether *adding more parallel lanes* (shape 1/2) beats one fresh-context single pass (shape 3). Anyone citing this paper for "parallel review lanes work better" would be over-reading it.
- No other numbers on parallel multi-lane vs. single-pass review turned up in the sources fetched this session.

## Verdict per candidate shape

**Shape 1 — SKILL.md procedure + each harness's native subagent facility.**
Supported for 3 of 5 (Claude Code, omp, DSH) with strong, harness-explicit primary sources, and functionally for Codex (docs say skill/AGENTS.md instructions can request delegation, though the docs are thinner and Codex's own skills page doesn't mention it). **Not supported for pi at all** — pi has no subagent facility a skill or anything else could trigger; a SKILL.md written for pi would have to fall back to shape 3 or route around pi entirely. Fresh context — the property the CCR paper says matters — is confirmed for Claude Code, omp, and DSH, and left ambiguous by Codex's own docs. Concurrency ceilings differ by an order of magnitude (omp default 32, Claude Code Agent tool 20 / Workflow 16, Codex 4 as configured here, DSH unbounded-by-convention) — a skill written generically would need to tolerate that instead of assuming a number. What's missing: no vendor or practitioner source describes a *review skill written once and run unmodified across all five harnesses* — each harness's spawning idiom (`agent()`/`parallel()` vs `tasks[]` vs `subagent`/`workflow` tool calls vs nothing) is different enough that "one SKILL.md" would really mean "one SKILL.md per harness dialect," which is close to shape 2's job description.

**Shape 2 — a minimal harness-independent runner.**
Headless invocation exists for all five (`claude -p`, `codex exec`, `pi -p`, `omp -p`, `dsh-headless`), so the mechanical precondition holds everywhere, pi included — this is the one shape that doesn't need pi to have a subagent facility, since the runner itself supplies the parallelism by launching N separate headless processes. In the wild, this exact shape is being built right now by several small, very recently active repos (all pushed within ~5 weeks of this survey) and by one large precedent (`claude-squad`, 8.5k★) for the adjacent "manage multiple CLI agent sessions" problem — but none of the review-specific runners found has meaningful adoption yet (0–40★), so "survived and matured" is not established, only "actively attempted." Missing: cost/plan-implication data for headless runs was not found for Codex or omp; Claude Code's own headless docs note structured JSON output and cost fields (`total_cost_usd`) are available, which a shape-2 runner would need per harness to normalize.

**Shape 3 — give up parallel lanes, use each harness's native single-pass review.**
Only 2 of 5 have a documented, dedicated single-pass review command: Claude Code's `/code-review` and Codex's `codex exec review` (confirmed locally, with flags for base/commit/uncommitted diffs). pi, omp, and DSH have **no dedicated review command** in the sources checked — omp has review-capable *agent types* (`reviewer`, `security-reviewer`) but only via the general `task` tool, not a one-shot review invocation; pi and DSH have neither a review command nor (for pi) any subagent facility to build one from inside the harness. The CCR paper is the strongest evidence *for* this shape's core premise (fresh-context review beats same-session review, p<0.01) but says nothing about whether it beats parallel lanes — so shape 3 is well-supported as "better than asking the same session to review its own work," not as "as good as multiple lanes." For 3 of 5 harnesses, shape 3 as stated would require building the "native single-pass review" feature that doesn't yet exist, which is most of the work shape 1/2 would also require.

## No precedent found

- A named practitioner's published, reviewed procedure for running the *same* multi-lane review across Claude Code, Codex, pi, omp, and DSH specifically.
- Any measured comparison of parallel multi-lane review vs. single fresh-context review (only same-session vs. fresh-session is measured, by CCR).
- A dedicated single-pass review command in pi, omp, or DSH.
- Billing/plan-tier differences for headless vs. interactive runs in Codex, pi, or omp (only Claude Code documents this, and only for `ultrareview`).
- A mature (well-starred, long-lived) harness-independent parallel-review runner — the closest adjacent precedent (`claude-squad`) is a session manager, not a review orchestrator, and every review-specific runner found is small and very recent.
- Direct confirmation (only ambiguity) of whether Codex subagents get fresh or inherited conversation context.
