# Nix flake vs mise as the single tool source for host AND agent box (2026-09-22)

Question: for this owner (macOS host defined by a Nix flake; mise for language runtimes; agent box = Docker Sandboxes `sbx` v0.43.0, Linux arm64 microVM whose custom templates must extend `docker/sandbox-templates:<agent>`), is the better single source of tools (a) the existing Nix flake, (b) mise, or (c) the current split (Nix for tools/LSP, mise for runtimes) — and what does it cost to get the Nix-defined tool set into the box?

This file extends `box-toolchain-provisioning.md` (same directory) and does not repeat it. Method: five parallel source-research passes (WebFetch, `gh api`, HN Algolia, NixOS Discourse API; WebSearch quota was exhausted for the whole session, so "not found" below means "not reachable with those tools", not proof of absence) plus **direct measurements on this machine and inside the real `docker/sandbox-templates:claude-code` image** (marked `[measured]`, script and raw output in the session scratchpad `linuxenv/`). Every external claim has a URL; quotes are verbatim; `[unverified]` marks inference; `[local]` marks facts from this repo/machine.

Short answer up front: the Nix flake is the only one of the three that already contains the whole list (73 CLI/LSP packages in `domains/dev/packages/home.nix`), 72 of 73 evaluate for `aarch64-linux` and 70 of those 72 are pre-built in cache.nixos.org at the flake's pinned nixpkgs revision. Measured in the real sbx base image: Determinate Nix installs in 5 s, the 13 language servers pull in 13–35 s (0.27 GiB download, 1.57 GiB unpacked), a 38-package box subset in 47 s (0.54 GiB download, 2.96 GiB unpacked), and every LSP binary runs as the non-root `agent` user without any host libc/cert/locale setup. The cost is real but bounded: the flake has to grow a per-system `packages.aarch64-linux` output (it is hard-coded to `aarch64-darwin` today), and the box gets a **second Nix store** (nothing is shared with the Mac's store; there is no local persistent volume in sbx, so the only cache is a baked template). mise cannot express half of the LSPs as first-class registry entries, its author explicitly rejects the Nix model, and no practitioner precedent was found for either tool doing "one definition → macOS host + Linux agent box". The practical recommendation (§8) is (c′): keep the split but make the Nix package list the single source for tools+LSP on both sides by giving it a Linux output and baking it into an sbx template; keep mise for runtimes via the same `mise.toml` in both places.

## 1. Nix inside a non-NixOS Linux container/VM (the sbx box)

### 1.1 Installer choice for a systemd-less, non-root-user Ubuntu image

- Determinate installer README (https://github.com/DeterminateSystems/nix-installer, section "In a container"): "In Docker/Podman containers or WSL2 instances where an init (like `systemd`) is not present, pass `--init none`." Warning: "When `--init none` is used, _only_ `root` or users who can elevate to `root` privileges can run Nix: `sudo -i nix run nixpkgs#hello`". Reference Dockerfile: `FROM ubuntu:latest` … `curl … https://install.determinate.systems/nix | sh -s -- install linux --extra-conf "sandbox = false" --init none --no-confirm` … `ENV PATH="${PATH}:/nix/var/nix/profiles/default/bin"`. "With some container tools, such as Docker, you can omit `sandbox = false`. Omitting this will negatively impact compatibility with container tools like Podman." Support table lists "Docker containers … ✓ Stable". Flake caveat: "You cannot lock a flake placed at the docker image root (`/`)" (https://github.com/DeterminateSystems/nix-installer/issues/1066).
- Design note behind `--init none`: "most people use the Single User variant for inside containers (like docker) or otherwise in build pipelines" (https://github.com/DeterminateSystems/nix-installer/issues/132). Container-specific bugs: #282 Alpine `useradd` missing (closed), #1305 "EBPF installation issue when building multiarch Docker images" (closed), #754 `nix-store --load-db` crash on kasm images (open).
- Upstream single-user installer in Docker as a non-root user fails with "error: could not set permissions on '/nix/var/nix/profiles/per-user' to 755: Operation not permitted"; the reported fix is `chown -R $USER /nix` plus `unset LC_ALL` (https://discourse.nixos.org/t/39060, 2024; fix is first-hand, root cause [unverified]).
- Devbox's own base image is the closest published precedent for "single-user Nix as a sudo-capable non-root user in a Debian image", including an arm64-specific tweak (https://raw.githubusercontent.com/jetify-com/devbox/main/internal/devbox/generate/tmpl/DevboxImageDockerfile):
  ```dockerfile
  FROM debian:stable-slim
  …
  RUN if [ "$TARGETPLATFORM" = "linux/arm64" ] || [ "$TARGETPLATFORM" = "linux/arm64/v8" ]; then \
          echo "filter-syscalls = false" >> /etc/nix/nix.conf; \
      fi
  ENV DEVBOX_USER=devbox
  RUN adduser $DEVBOX_USER
  RUN usermod -aG sudo $DEVBOX_USER
  …
  USER $DEVBOX_USER
  RUN wget --output-document=/dev/stdout https://nixos.org/nix/install | sh -s -- --no-daemon
  ENV PATH="/home/${DEVBOX_USER}/.nix-profile/bin:$PATH"
  ```
- `[measured]` In `docker/sandbox-templates:claude-code` (Ubuntu 26.04 LTS, aarch64, user `agent` uid 1000 with sudo, 14 CPUs / 15 GB in the Docker VM), the Determinate route works unchanged: `sudo sh install … --init none --no-confirm` exits 0 in **5 s** on three runs; `/nix` is **220 MB** after install; result "nix (Determinate Nix 3.22.5) 2.35.2". `/nix/store` is `root:nixbld`, so `agent` cannot write it and must use `sudo -i nix …` (exactly the README warning) — acceptable in sbx because `agent` has passwordless sudo, but it means the *agent process* cannot `nix profile add` without sudo.

### 1.2 `nix profile add` / `nix build` of a shared `packages.<system>` list

- The host flake today has no per-system package output: `core/nix/flake.nix` sets `system = "aarch64-darwin";` once and exposes only `darwinConfigurations.${hostname}` [local]. `domains/dev/packages/home.nix` is a `home.packages` list (73 CLI/LSP attrs plus 6 `brewCasks` and darwin-only `mas`, `nowplaying-cli`, `cocoapods`) [local]. So "share the list" means factoring that list into a function of `pkgs` and exposing it both as `home.packages` and as `packages.aarch64-linux.<name> = pkgs.buildEnv { paths = … }`.
- Pattern sources: flake-utils README (https://github.com/numtide/flake-utils): `defaultSystems` "= `["x86_64-linux" "aarch64-linux" "x86_64-darwin" "aarch64-darwin"]`"; `eachDefaultSystemPassThrough` exists "for outputs like `homeConfigurations`/`nixosConfigurations` that must NOT be keyed by system". Hand-rolled equivalent from Eelco Dolstra's own flake (https://github.com/edolstra/dwarffs/blob/master/flake.nix): `forAllSystems = f: nixpkgs.lib.genAttrs supportedSystems (system: f system);`. `nix profile add` (2.34+ name of `install`) takes any installable, e.g. `.#devtools` (https://nix.dev/manual/nix/2.24/command-ref/new-cli/nix3-profile-install.html).
- `[measured]` A scratch flake pinning the same nixpkgs revision as `core/nix/flake.lock` (`b86751bc…`, 2026-04-16) and listing the 73 attrs: **72/73 evaluate for `aarch64-linux`** (only `codebase-memory-mcp` is missing — it comes from the repo overlay, not nixpkgs; nothing is marked unsupported/broken on Linux). Evaluation of the list: 8.6 s cold, ~3 s warm on the Mac.
- `[measured]` mise itself is in that list and is installed by Nix on the host (`mise 2026.4.6` at `/etc/profiles/per-user/<user>/bin/mise`) [local]. The "current split" is therefore already "Nix installs mise, mise installs runtimes".

Magic Nix Cache claims "Save 30-50%+ of CI time" (https://github.com/DeterminateSystems/magic-nix-cache-action) — relative only. nix2container's README benchmarks image rebuild+push at ~1.8 s vs `dockerTools.streamLayeredImage` ~7.5 s vs `buildImage` ~10 s, self-described as "quick and dirty" (https://github.com/nlewo/nix2container).

### 1.4 Caching the store across sandbox recreations

- sbx has no local persistent volume: `sbx create -v/--volume` is "(cloud only, experimental)" and `sbx volume` is "Manage persistent volumes (cloud-only)"; `-t, --template string  Container image to use for the sandbox (default: agent-specific image)` is the local persistence mechanism [local, `sbx create --help` v0.43.0]. Kit install commands re-run per creation (prior file §1.9). So locally the choices are: (i) re-download per create (47 s + network allowlist for `install.determinate.systems`, `cache.nixos.org`, `github.com`; the claude kit currently allows only `ports.ubuntu.com`, `archive/security.ubuntu.com`, `mise.run`, `mise.jdx.dev`, `github.com` [local, `spec.yaml.in`]), or (ii) bake into a template image (§2).
- Volume-at-`/nix` pitfall, documented by the devcontainers Nix feature: "On 1.3.x, Due to a nix cache `version`/`packages` changes are silently ignored on rebuild. `/nix` is mounted from a Docker volume that is seeded only on the first build. That mount can't be modified afterwards, so it keeps masking the newer image and no option change ever takes effect." 1.4.0 removed the default cache (https://github.com/devcontainers/features/tree/main/src/nix; issue https://github.com/devcontainers/features/issues/1505: "docker copies content into a volume **only** if the volume is empty"). Options of that feature: `version`, `multiUser` (default true), `packages`, `useAttributePath`, `flakeUri`, `extraNixConfig`; "Currently `flakeUri` works best with a remote URI … as local files need to be in the image." Podman fails at feature build: "error: cannot set host name: Operation not permitted" (https://github.com/devcontainers/features/issues/299, open). No install-time or size numbers in any of those issues.
- Alternatives with precedent but no numbers: `harmonia` ("serves your /nix/store as a binary cache over http", https://github.com/nix-community/harmonia), `attic` (2,080 stars; an R2-backed deployment notes "256MB of RAM was not enough", https://lgug2z.com/articles/deploying-a-cloudflare-r2-backed-nix-binary-cache-attic-on-fly-io/). A LAN cache served from the Mac would let the box pull from the Mac's store only for paths that exist there — but the Mac store holds `aarch64-darwin` builds, so almost nothing would hit [unverified; follows from per-system store paths].

### 1.5 Binary-cache coverage for aarch64-linux

- nixpkgs manual: Hydra "builds binary packages from the Nix expressions in Nixpkgs for `x86_64-linux`, `aarch64-linux`, `x86_64-darwin` and `aarch64-darwin`. The binaries are made available via a binary cache" (https://nixos.org/manual/nixpkgs/stable/). RFC 46 (Nov 2019 snapshot) puts native `aarch64-linux` in Tier 2: "Most packages work, credible ambition to reach Tier 1 coverage at some point" (https://raw.githubusercontent.com/NixOS/rfcs/master/rfcs/0046-platform-support-tiers.md). No published hit-rate statistic found.
- `[measured]` at revision `b86751bc`: **70 of 72** top-level packages present in cache.nixos.org for aarch64-linux. Misses: `terraform-1.14.8` (`meta.license = bsl11`, `unfree = true` — Hydra never builds unfree, so it would compile in the box or need `opentofu`) and `wrangler-4.62.0` (MIT, but absent for x86_64-linux and aarch64-darwin as well — a Hydra build gap, not an arm64 gap). Everything else, including all 12 LSPs and `gopls`, was substituted, none built.

## 2. Building an OCI layer from the flake on top of `docker/sandbox-templates:<agent>`

### 2.1 What the Nix image tools can and cannot do here

- `dockerTools.buildImage`/`streamLayeredImage` `fromImage`: "The repository tarball of an image to be used as the base for the generated image. It must be a valid Docker image, such as one exported by `docker image save`, or another image built with the `dockerTools` utility functions. This can be seen as an equivalent of `FROM fromImage` in a `Dockerfile`." Arbitrary registry images come in via `dockerTools.pullImage` (digest-pinned). `maxLayers` "Default value: 100" and "the number of layers used by `fromImage` will be subtracted". `includeNixDB` "CAUTION: Be careful since this doesn't work well in combination with `fromImage`". `contents` is deprecated for `copyToRoot`. `exportImage` "requires the `kvm` device". Ownership: `uid`/`gid` "Default value: 0 / 0 / 'root' / 'root'" (https://nixos.org/manual/nixpkgs/stable/#sec-pkgs-dockerTools).
- nix2container: `fromImage` "an image that is used as base image of this image; use `pullImage` or `pullImageFromManifest` to supply this" with an Alpine example (https://github.com/nlewo/nix2container). Works for any registry image by digest, so `docker/sandbox-templates:claude-code` is expressible [unverified: not exercised].
- Building any of these **on the Mac** needs a Linux builder: devenv says "To be able to generate containers on macOS, you will need to use a remote Linux builder" (https://devenv.sh/containers/). devenv containers use nix2container underneath; flox `containerize` has no base-image flag (https://flox.dev/docs/man/flox-containerize/); `devbox generate dockerfile` templates `FROM docker.io/jetpackio/devbox:latest`, not an arbitrary base (https://github.com/jetify-com/devbox `internal/devbox/generate/tmpl/*.Dockerfile.tmpl`). Devbox deliberately skips `nix-store --optimise` in Docker: "on Docker's default overlay2 storage driver the rename it performs fails with 'cannot rename: Stale file handle'" (https://github.com/jetify-com/devbox/issues/2616).
- Conclusion: none of the four Nix image builders emits "a layer you append to an existing Ubuntu base" without a Linux Nix builder in the loop; the plain-Dockerfile multi-stage pattern below does, and `docker build` on the Mac already targets linux/arm64.

### 2.2 Precedent for `COPY --from=nix-builder /nix/store` onto a non-Nix base

- Mitchell Hashimoto, "Nix with Dockerfiles" (https://mitchellh.com/writing/nix-with-dockerfiles): `FROM nixos/nix:latest AS builder` … `RUN nix … --option filter-syscalls false build` … `RUN cp -R $(nix-store -qR result/) /tmp/nix-store-closure` … `FROM scratch` … `COPY --from=builder /tmp/nix-store-closure /nix/store`. "Final image is based on scratch. We copy a bunch of Nix dependencies but they're fully self-contained so we don't need Nix anymore." Downside: "The single RUN nix build command produces a giant layer with all the dependencies in it … every redeploy will require your runtime environment to redownload the largest layer of your image."
- Docker's own `docker/labs-ai-tools-for-devs` layers a Nix closure onto a non-scratch, non-Nix base (`FROM babashka/babashka:latest@sha256:…` … `COPY --from=builder /tmp/nix-store-closure /nix/store`) and caches the builder store with `RUN --mount=type=cache,target=/nix,from=nixos/nix:2.21.1,source=/nix` (https://raw.githubusercontent.com/docker/labs-ai-tools-for-devs/main/functions/hub/Dockerfile.template).
- moq-dev/moq does the same with the comment "It's difficult to cross compile Docker images with Nix… Nix is not required for developers; `docker build .` will work." (https://raw.githubusercontent.com/moq-dev/moq/main/Dockerfile).
- Nix binaries are self-contained by construction: nix-ld's README explains NixOS "usually has its dynamic linker in the glibc package in the Nix store" and that nix-ld is for *foreign* binaries, "Normal Linux distributions will have their own link-loader. Replacing those with nix-ld will break the system." (https://github.com/nix-community/nix-ld). `[measured]` §1.3 confirms: every LSP ran on Ubuntu 26.04 with no host glibc involvement.
- Pitfalls, with status: (1) ownership — `COPY` preserves root ownership; fine for read-only execution, and `agent` needs `sudo` only to run `nix` itself [measured: `touch /nix/store/x` → permission denied, binaries run]; (2) missing `/nix/var/nix/db` — irrelevant unless `nix` is invoked in the runtime image (manual's `includeNixDB` note); (3) certs — the manual says add `pkgs.cacert` if you see "certificate has unknown CA", but `[measured]` nix-built `gh`/`git` used Ubuntu's `/etc/ssl/certs` unaided; (4) `LOCALE_ARCHIVE` — nixos.wiki is Cloudflare-gated and could not be fetched; `[measured]` no warnings from `git`/LSPs with `LANG` unset; (5) `nix-store --optimise` on overlay2 (devbox #2616 above); (6) PATH order vs Ubuntu's own `node`/`rg`/`jq` [local] — no source names this; it is a design choice.

### 2.3 `[measured]` The two bake routes as real sbx templates

Both built with plain `docker build` on this Mac (Docker 29.4.0, linux/arm64), from the scratch flake's 38-package `subset` output, `FROM docker/sandbox-templates:claude-code` (2.48 GB):

| Route | Dockerfile shape | Build wall time | Image size | `/nix` in image | `nix` CLI in image | LSPs run as `agent`? |
|---|---|---|---|---|---|---|
| A: Nix installed in the template | `USER root` → Determinate installer `--init none` → `COPY flake.nix flake.lock` → `nix profile add /src#subset` → `nix store gc` → `ENV PATH=/nix/var/nix/profiles/default/bin:$PATH` → `USER agent` | **1 min 33 s** | **7.2 GB** | 3,462 MB | yes (`sudo -i nix`, Determinate Nix 3.22.5) | yes (`gopls v0.21.1`, `gh 2.89.0 (nixpkgs)`) |
| B: multi-stage closure copy | `FROM nixos/nix:latest AS builder` → `nix build /src#subset` → `cp -R $(nix-store -qR result) /tmp/closure` → `FROM docker/sandbox-templates:claude-code` → `COPY --from=builder /tmp/closure /nix/store` → symlink result to `/opt/devtools` → `ENV PATH=/opt/devtools/bin:$PATH` → `USER agent` | **1 min 52 s** (includes pulling `nixos/nix`) | **6.79 GB** | 3,226 MB (260 store paths, no nixpkgs source, no Nix) | no | yes (`gopls v0.21.1`, `typescript-language-server 5.1.3`, `gh 2.89.0`) |

Both images are usable as `sbx create claude -t <image>` templates by construction (same base, `agent` user preserved); `sbx create` with them was **not** run this session, so microVM boot latency with a ~7 GB image is unmeasured. Docker's layer cache makes rebuilds free until `flake.lock` or the list changes; then the whole ~3.3 GB layer is rebuilt (Hashimoto's caveat). Route B is 0.4 GB smaller and has no root-only `nix` surface; route A lets the agent (via sudo) add tools from the same pinned nixpkgs at runtime.

## 4. mise vs Nix head-to-head

### 4.1 The mise author's stance

- "I think the entire concept of nix is a broken model not fixable by docs and better DX. Precompiled, portable binaries are the way to go which is what mise is built on. Trying to maintain this separate build chain where everything is compiled in a sandbox gives your system a 'split-brain' problem where you have the 'nix world' and the 'macos (or whatever) world'." — jdx, https://news.ycombinator.com/item?id=42359686 (2024-12-08). "I started writing mise in a bout of frustration after trying to use nix" (https://news.ycombinator.com/item?id=42359499). "docker and nix try to _bypass_ your environment by building their own. Mise augments your environment" (https://news.ycombinator.com/item?id=40192709). "I think of mise as an overlay on existing systems, not a system in itself." (https://news.ycombinator.com/item?id=48043531, 2026-05-06).
- No Nix *tool* backend exists or is planned: in https://github.com/jdx/mise/discussions/1250 `nix?` stayed an unchecked box; a contributor: "nix, pnpm and eget are DOA, no way to get them into the right paths". The registry's backend tiers (packslip → aqua/github/gitlab → conda → pipx/npm/gem/go/cargo/dotnet) never list nix, and "New vfox and asdf tools are not accepted for supply-chain security reasons … The ubi backend is deprecated" (https://mise.jdx.dev/registry.html).
- What does exist (new, lastmod 2026-09-09): a **`nix` bootstrap package manager**, peer of `brew`/`apt`: "The `nix` bootstrap package manager installs packages into the current user's normal Nix profile. It works on Linux and macOS with Nix on `PATH`." … `[bootstrap.packages] "nix:ripgrep" = "latest"` … "mise does not create shims for them or invoke sudo" … mise "does not install Nix, configure caches, update flake lockfiles itself, or add fallback sources", and `mise bootstrap packages export --format nix > packages.nix` (https://mise.jdx.dev/bootstrap/packages/nix.html). This is mise *driving* a Nix profile, i.e. an admission that system tools belong to a package manager, not a version manager; it does not pin nixpkgs, so it is weaker than the flake for reproducibility [inference].
- No dedicated "mise vs nix" or "devbox vs mise" HN thread exists (0 Algolia hits for either phrase).

### 4.2 Pinning and reproducibility

- mise: per-tool `os = ["linux", "macos"]`, `"macos/arm64"`, `"linux/x64"` (https://mise.jdx.dev/dev-tools/); `mise.lock` records `[tools.node."platforms.macos-arm64"] checksum = … url = …` and `mise lock --platform linux-x64,macos-arm64` pre-populates; platforms without an artifact are "reported as skipped rather than locked"; URL/checksum locking "skip[s] backends that cannot record a download URL: `asdf`, `cargo`, `gem`, `go`, `npm`, `pypi`/`pipx`, `ubi`, `core:dotnet`, `core:rust`, `core:swift`, and vfox" (https://mise.jdx.dev/dev-tools/mise-lock.html). For this owner's LSP list that means `gopls`, `typescript-language-server`, `bash-language-server`, `yaml-language-server`, `vscode-langservers-extracted`, `tailwindcss-language-server`, `astro-language-server` (all `go:`/`npm:`) are never URL-locked, and `nixd` has no mise route at all except `nix:` bootstrap (prior file §2.2 registry check; `nixd` absent).
- Nix: one `flake.lock` revision pins every package on every system; `[measured]` 72/73 evaluate on aarch64-linux from the same lock, 70/72 substituted. The cost side: unfree packages (terraform) are never cached; `wrangler` was uncached on all three systems at this revision.

### 4.3 Supply chain

- mise: "mise implements checksum, GitHub artifact attestation, Cosign, SLSA, and Minisign verification natively… Support in the backend does not mean that every package supplies all of these checks." (https://mise.jdx.dev/dev-tools/backends/aqua.html). github backend: checksum/provenance are opt-in per entry or via lockfile (https://mise.jdx.dev/dev-tools/backends/github.html). "An asdf plugin executes shell code during tool management." (https://mise.jdx.dev/dev-tools/comparison-to-asdf.html). Paranoid mode "does not sandbox a command after you approve it" (https://mise.jdx.dev/paranoid.html); `minimum_release_age` default 24 h (https://mise.jdx.dev/security.html). The installer is still `curl https://mise.run | sh` [local, kit]. No mise/asdf supply-chain incident surfaced.
- nixpkgs: xz backdoor revert PR #300028 opened 2024-03-29T16:20Z, merged 17:17Z (57 min) (https://github.com/NixOS/nixpkgs/pull/300028); tracking issue #300055 open ~5.5 days; a contemporaneous post complained "it has been nearly 5 days and the reversion to xz 5.4.6 has still NOT made its way into the unstable branch" because Hydra channel promotion lagged (https://shadeyg56.vercel.app/posts/nixos/xz-backdoor/).

### 4.4 macOS updates breaking Nix

- Sequoia: NixOS/nix#10892 "macOS 15 Sequoia clobbers _nixbld1-4 users" (open as a living doc; fix in Nix 2.24.6+ and backports); nix-darwin#970 opened 2024-06-11, closed 2024-09-11 (https://github.com/nix-darwin/nix-darwin/issues/970).
- Tahoe: NixOS/nix#13342 "Nix daemon crash on macOS 26 Beta" opened 2025-06-10, closed 2025-09-18, with "Determinate Nix works fine" while upstream/Lix crashed (https://github.com/NixOS/nix/issues/13342); nix-darwin#1544 `darwin-rebuild: command not found` (open), #1621 "Tahoe modified /etc/zshrc and /etc/zprofile" (closed same day, but "Nope, still an issue!" on 2026-03-22), #1577 `$TMPDIR` (open).
- Determinate: "Nix installations from the Determinate Nix Installer after version v0.14 survive macOS upgrades … creates a global Launch Daemon which restores the necessary pieces of Nix's installation at boot time." (https://determinate.systems/posts/nix-survival-mode-on-macos/, 2023-10-25); "over 7 million installs" (README). The host runs Nix 2.34.6 via nix-darwin [local]; whether it is the Determinate build was not checked.
- mise has no equivalent failure class; its macOS risk is the ordinary "shim PATH not visible to non-shell processes" (prior file §2.2, cosai ADR).

### 4.5 Evaluation / switch time

- HN data points: `home-manager switch` "can take a good 15 seconds or so" (2022, https://news.ycombinator.com/item?id=33315345); `darwin-rebuild switch` "~1s without the homebrew commands… ~4s the first time and ~1.5s in subsequent runs" (2024, https://news.ycombinator.com/item?id=40161415); with brew bundle "turns something that could take 1 second into something that takes 10" (2026-03-24, https://news.ycombinator.com/item?id=47503212). `[measured]` evaluating the 73-package list for aarch64-linux: 8.6 s cold / ~3 s warm on this Mac.
- mise publishes no numeric benchmark page (https://mise.jdx.dev/dev-tools/shims.html is qualitative).

## 5. LSP specifically

Contrast `programs.pi-coding-agent.extraPackages`: "These are added to the PATH of the wrapped pi binary." Claude Code's docs: `command` is "The LSP binary to execute (must be in PATH)"; no user-level `~/.claude/lsp.json` exists (https://code.claude.com/docs/en/plugins-reference).
- Other harness modules in home-manager: `programs.codex` (settings → `CODEX_HOME/config.toml`, profiles, hooks, plugins, skills, rules; no LSP, MCP via `settings.mcp_servers`), `programs.pi-coding-agent` (settings, keybindings, models, context, `extraPackages`; no LSP), `programs.opencode`, `programs.crush`, `programs.aider-chat`. **No `programs.dsh`, no `programs.gemini-cli`** (only `antigravity-cli-legacy` [unverified whether that is gemini-cli's successor]). **No Nix module writes LSP config for codex/pi/dsh.**
- Known module breakage: home-manager #9831 "Claude Code deletes `~/.claude/settings.json` because the module symlinks it into the store" (open), #9906 plugins layout refused by Claude Code ≥ 2.1.257 (open), #9655/#9689 store-watching (closed) — https://github.com/nix-community/home-manager/issues/<n>.
- This host uses none of that: LSP wiring is the official marketplace plugins `gopls-lsp`, `rust-analyzer-lsp`, `swift-lsp` [local, `~/.claude/plugins/installed_plugins.json`], and the binaries come from `home.packages`. So Nix already supplies the LSP *binaries* on the host; the *wiring* is per-agent and would stay per-agent in the box (Claude plugins, DSH profile), exactly as the prior file's §7.2 concluded.
- Do nixpkgs LSP binaries work under Claude Code? No issue found saying they do not on a non-NixOS host; the NixOS-specific one (#16080, closed) was about FHS path assumptions. `[measured]` all 13 run on Ubuntu as `agent`. The remaining risk is PATH inheritance (#63596), which is a box-image `ENV PATH` question, not a Nix question.

## 7. What it costs to get the Nix-defined tool set into the sbx box (concrete)

1. Flake refactor: turn `domains/dev/packages/home.nix` into `{ pkgs }: { cli = [...]; lsp = [...]; darwinOnly = [...]; }`, keep `home.packages = cli ++ lsp ++ darwinOnly ++ casks`, add `packages.aarch64-linux.box = pkgs.buildEnv { paths = cli ++ lsp; }` using `nixpkgs.lib.genAttrs`. Evaluation needs `--impure` today because `username = builtins.getEnv "USER"` [local, flake.nix] — the box output should not depend on it. `codebase-memory-mcp` and the `gh` trunk override live in `overlays.nix` and must be applied in the Linux `import nixpkgs` too (they evaluated fine on Linux only because the scratch flake dropped the overlay package). `terraform` → drop from the box list or accept a local build; `wrangler` is uncached on all systems at this revision.
2. Box network policy (kit route only): add `install.determinate.systems`, `cache.nixos.org`, and keep `github.com` (nixpkgs tarball, 315 MB) [local + measured]. Template route needs none of this at create time.
3. Time and size: 5 s + 47 s per create (kit route) or once per template build; `/nix` ≈ 4 GB in the box for the 38-package subset, ≈ 6 GB for the full list [measured/extrapolated from 5.34 GiB closure].
4. PATH: prepend `/nix/var/nix/profiles/default/bin` (or the closure's `bin`) in the image `ENV`, not in a shell rc, so that agents launched by the sandbox entrypoint and their LSP children see it (Claude Code #63596; cosai ADR VS Code Server finding). Decide whether Nix `node`/`rg`/`jq` should shadow Ubuntu's.
5. Two stores: the Mac's store (aarch64-darwin) shares nothing with the box's (aarch64-linux); there is no local sbx volume to persist `/nix`; the only reuse is Docker's image layer cache, which is invalidated whenever the flake lock or list changes (Mitchell Hashimoto's "giant layer" caveat).

## 8. Recommendation for this owner

Choose **(c′)**: keep mise for language runtimes and make the existing Nix package list the single source for CLI tools and language servers on both host and box, by giving the flake a Linux output and baking it into an sbx template.

Evidence it rests on: the list already exists and is the working host definition [local]; 72/73 attrs evaluate for Linux and 70/72 are pre-built for aarch64-linux at the pinned revision `[measured]`; the real sbx base image accepts Determinate Nix in 5 s and the whole box subset in 47 s, and every LSP binary runs as `agent` with no glibc/cert/locale fixes `[measured]`; the closure-copy pattern onto a non-Nix base has precedent from Docker's own org and from Hashimoto; mise cannot carry `nixd` at all and cannot URL-lock the `go:`/`npm:` LSPs, and its author's design position is the opposite of "one pinned set" (§4.1–4.2). Runtimes stay in mise because that is where they are, the metabase `COPY mise.toml` pattern is proven, and moving nine runtimes into Nix is not needed to solve the box problem.

Prefer the template over the kit route: sbx has no local persistent volume, kit installs re-run on every create, and 52 s + 0.8 GB of downloads per create is the recurring alternative. Prefer "Nix installed in the image" (route A) over closure-copy (route B) only if the agent should be able to `nix profile add` more tools itself with sudo; otherwise B is smaller and has no `nix`/nixpkgs-source overhead (see §2.3 numbers).

What is missing: (1) no practitioner does exactly this, so the flake-refactor ergonomics (overlays on Linux, `--impure` username, per-agent template rebuilds) are unproven beyond this session's scratch flake; (2) no measurement of template *create* latency with a 6–7 GB image under sbx's microVM (image size may matter more there than in `docker run`); (3) the mise runtime half in the box was not re-measured here (prior file §2.2/§7); (4) LSP wiring for DSH/pi inside the box remains per-agent config, unchanged by this decision; (5) whether Claude Code's LSP plugin actually starts servers inside an sbx sandbox (as opposed to cloud sessions where it is disabled) was not tested.
