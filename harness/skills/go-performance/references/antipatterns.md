# Go Performance Anti-Patterns

25 patterns worth flagging in review. **static** = the code shape alone is
the problem, flag it unconditionally. **measure** = plausible but the cost
depends on hot-path frequency and data size — confirm with a profile before
calling it a fix, per the measure-first loop in `SKILL.md`.

| # | Pattern | Why it costs | Fix | Tag |
|---|---|---|---|---|
| 1 | `defer mu.Unlock()` (or any defer) inside a loop body, not the enclosing function | Each `defer` in the loop accumulates until the *function* returns, not the loop iteration — a long loop builds a large defer stack and delays every unlock | Extract the loop body into its own function, or manage the lock manually without defer inside the loop | static |
| 2 | String building with `+`/`+=`/`fmt.Sprintf` in a loop | Each concatenation allocates a new string; O(n²) total work for n appends | `strings.Builder` with `Grow(n)` if size is known | static |
| 3 | `regexp.Compile`/`MustCompile` called inside a loop or on every function call | Compiling a regex is expensive relative to matching; recompiling per call throws that cost away every time | Compile once as a package-level `var` or lazily via `sync.Once` | static |
| 4 | `[]byte(s)` / `string(b)` conversions in a hot path | Both copy the underlying data; repeated conversions of the same value do redundant copying | Keep one representation through the hot path, or use `unsafe`-free `strings.Builder`/`bytes.Buffer` APIs that avoid the round-trip | measure |
| 5 | Unbounded `go func()` per input item in a loop over user-controlled or large input | No backpressure — a large or malicious input spawns unbounded goroutines, exhausting memory/scheduler | `errgroup.Group.SetLimit(n)` or a sized semaphore | static |
| 6 | Decoding JSON into `interface{}`/`map[string]any` when the shape is known | Reflection-based, allocation-heavy, and loses type safety compared to a typed struct | Define a struct and unmarshal into it directly | measure |
| 7 | Query-per-row in a loop (N+1) | One round trip per row instead of one batched query — dominates latency under real data volumes | Batch with `IN (...)`, a join, or `sqlc`/ORM eager-loading, or a single `SELECT` keyed on the ID set | static |
| 8 | Cache or in-memory map with no eviction policy or size bound | Grows without limit; since Go maps never shrink after deletes, even bursty peaks leave the memory allocated permanently | Bound with an LRU (`golang-lru`), a TTL sweep, or a max-size check on insert | static |
| 9 | `append` in a loop with a statically knowable final length and no `cap` hint | Repeated reallocation and copy as the slice grows past its capacity | `make([]T, 0, n)` before the loop when `n` is known or estimable | measure |
| 10 | `resp.Body`/`io.ReadCloser` not closed on every return path (including early error returns) | Leaks the underlying connection; for `http.Response.Body`, blocks connection reuse in the pool | `defer resp.Body.Close()` immediately after the nil-error check | static |
| 11 | `time.Now()` called many times per hot-loop iteration for the same logical "now" | Each call is a runtime call (monotonic + wall clock read); usually cheap alone but adds up at high call rates and hides intent | Call once per iteration/request, pass the value down instead of re-querying | measure |
| 12 | Logging with expensive arguments not guarded by level check (`slog.Info("x", "y", expensive())`) | `slog`/`log` argument expressions are evaluated eagerly even if the message is filtered out by level | Guard with `logger.Enabled(ctx, level)`, or pass a `slog.LogValuer` for lazy evaluation | measure |
| 13 | `sync.Pool` used for small, cheap-to-allocate objects | Pool bookkeeping (interface boxing, per-P local pools, victim cache) can exceed the cost of a plain allocation for small objects | Only pool objects large/expensive enough that the allocation itself is the bottleneck (profile first) | measure |
| 14 | `sync.Pool` objects held across GC cycles expecting reuse | Pool contents can be cleared on any GC; code that assumes "put it back, get it later" survives GC is wrong and silently reallocates | Treat Pool as a same-cycle scratch buffer only, not a long-lived cache | static |
| 15 | Passing large structs by value through a hot call chain instead of by pointer | Each call copies the full struct; compounds across a deep call chain | Pass by pointer once the struct is large enough that copy cost is measurable, keep small structs by value | measure |
| 16 | Struct with hot fields written by different goroutines packed onto the same cache line | False sharing — CPU cache-line invalidation between cores serializes what looks like independent writes | Pad hot per-goroutine fields to separate cache lines (64 bytes); do not run a generic field-reordering tool without checking this | measure |
| 17 | Interface value used purely for a single implementation with no plan for a second | Adds an indirection and defeats devirtualization/inlining for no abstraction benefit | Use the concrete type directly until a second implementation actually exists | static |
| 18 | Generic function that type-switches on its own type parameter inside the body | The type parameter buys nothing if the body still branches per type — that's what an interface is for | Convert to an interface method, or split into type-specific functions | static |
| 19 | `context.WithValue` used to pass optional parameters or dependencies (not request-scoped data) | Turns function signatures opaque, defeats type safety, and each lookup is a linear walk up the context chain | Pass parameters/dependencies explicitly; reserve context values for cross-cutting request-scoped data (trace ID, auth) | static |
| 20 | Unbuffered `http.Transport` reused with default `MaxIdleConnsPerHost=2` under high fan-out to one host | Connections get opened and torn down repeatedly instead of reused, adding TCP/TLS handshake cost per request | Set `MaxIdleConnsPerHost`/`MaxIdleConns` to match real concurrency to that host | measure |
| 21 | `database/sql` pool left at default (unbounded open conns) under load | Can exceed the database's own max-connections limit, causing connection errors upstream instead of graceful queuing | `SetMaxOpenConns`/`SetMaxIdleConns`/`SetConnMaxLifetime` sized to the DB's budget | static |
| 22 | Manually pinning `GOMAXPROCS` to host `NumCPU` in a container with a lower cgroup CPU limit | Oversubscribes the actual quota, causing throttling (a full-process pause) instead of Go's own multiplexing overhead | Rely on Go ≥1.25's container-aware default, or set explicitly to the cgroup limit if not | static |
| 23 | Ballast object (large unused slice) kept in a service to control GC pacing | Obsolete workaround from before `GOMEMLIMIT` (1.19); adds a permanent large allocation for a job `GOMEMLIMIT` now does directly | Delete the ballast, set `GOMEMLIMIT` instead | static |
| 24 | `runtime.SetFinalizer` used for cleanup of an object with cyclic references, or where prompt reclamation matters | Finalizers resurrect the object, delaying GC of everything it references; finalizer + cycle can leak indefinitely in adversarial cases | `runtime.AddCleanup` (1.24) — cleanup argument is separate from the object, no resurrection | static |
| 25 | Passing a value to a variadic `...any`/`...interface{}` parameter in a hot path (e.g. `fmt.Sprintf`, a generic logging call) | Boxes the value into an interface, forcing a heap allocation even for a value that would otherwise stay on the stack | Use a typed, non-variadic path in the hot loop; reserve the variadic call for cold paths | measure |
